# PayU India (adapter id `payu_india`): provider research

Status: research notes for a parse-only PandaPayLens adapter. Nothing here is a guarantee about live behavior. Everything comes from PayU India's first-party documentation (`docs.payu.in`), PayU India's own website (`payu.in`) and PayU India's official SDK repositories as published on the verification date. When a point is not documented, the text says **NOT DOCUMENTED**.

- Verification date: **2026-10-25**
- Gate outcome: **documentation_verified**
- Scope: PayU India only (PayU Payments Private Limited, hosts `*.payu.in`). PayU's platforms in other regions use different APIs and are not covered; nothing in this file applies to them.
- Method: pages were discovered through the documentation site's own `robots.txt`, `sitemap.xml` and `llms.txt` indexes and read in their Markdown form (the same page URL with `.md` appended, which the site's `llms.txt` index links to). The `updatedAt` value listed for each page is the page's own metadata. Several code tables on the Error Codes page are rendered from JSON files that the page itself loads from `raw.githubusercontent.com/palgunams21/payu-docs-assets`; those JSON files were downloaded and every code in section 4 was checked mechanically against them, so code values are exact; meanings are paraphrased.
- Legacy names: the docs still use the internal name "ibibo code" for payment option codes (`ibibo_code` field, `INTNEGATIVE` described as an invalid IBIBO code) and mention PayUMoney as an older product whose `_payment` endpoint is the same. Payloads and logs may therefore contain either name.

### 2. API families and versions in scope

| Family                                                                      | Endpoint(s) / delivery                                                                                                                                                                              | Format                                                                                         | Relevance                                                                                                    |
| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Payment response (`_payment`)**                                           | Browser form POST from PayU to the merchant `surl` / `furl` (and `curl` for cancel) after `https://secure.payu.in/_payment` (test `https://test.payu.in/_payment`)                                  | `application/x-www-form-urlencoded` name-value pairs                                           | **Primary.** The most common paste. Same vocabulary as the payment webhook                                   |
| **Payment webhooks** (events Successful, Failed)                            | Server POST to URLs configured in the Dashboard, or per transaction through `partner_webhook_success` / `partner_webhook_failure`                                                                   | Form-encoded (D/webhook-events-and-sample-payloads: "Form POST URL Encoded format")            | **Primary.** PayU calls the S2S webhook "the primary source of truth" (D/prebuilt-checkout-page-integration) |
| **Verify Payment / Check Payment APIs**                                     | `POST https://info.payu.in/merchant/postservice.php?form=2` (test `https://test.payu.in/merchant/postservice.php?form=2`), `command=verify_payment` (by `txnid`) or `check_payment` (by `mihpayid`) | Form-encoded request; JSON response with `form=2`                                              | **Primary** for reconciliation and pending payments                                                          |
| Transaction listing                                                         | Same endpoint, `get_Transaction_Details` (date range), `get_transaction_info` (time range)                                                                                                          | JSON (`Transaction_details` array)                                                             | Secondary; different field names (`id`, `bank_ref_no`, `ibibo_code`)                                         |

| Refund webhook / refund status callback, refund ARN callback                | POST to a configured refund URL                                                                                                                                                                     | JSON (`application/json`); ARN callback is a bulk JSON object keyed by merchant transaction ID | Secondary                                                                                                    |
| Dispute (chargeback) webhook                                                | POST to a configured URL; optional signature headers                                                                                                                                                | JSON                                                                                           | Secondary; the only documented push channel for chargebacks                                                  |
| S2S payment API                                                             | `_payment` with `txn_s2s_flow` (4 = S2S, 3 = direct authorization)                                                                                                                                  | JSON with `metaData`, `result`, `binData`                                                      | Secondary; interim (redirect/OTP) responses, not final status                                                |
| Capture of pre-authorized payments                                          | Command API (R/capture_a_payment)                                                                                                                                                                   | JSON                                                                                           | Secondary                                                                                                    |
| Settlement APIs                                                             | `GET https://info.payu.in/settlement/transactionDetails`, `/settlement/range` (test `https://apitest.payu.in/...`), HMAC `authorization` header with `date`                                         | JSON (`code`, `message`, `status`, `result`)                                                   | Later; settlement timeline                                                                                   |
| Chargeback APIs                                                             | Token-based JSON:API style (`data.type = "chargebacks"`, kebab-case attributes)                                                                                                                     | JSON                                                                                           | Later                                                                                                        |

Versions: the `_payment` request takes `api_version` (R/addl_info-payment-apis says "Must be passed as 7"; D/hashing-request-and-response gives a different hash for `api_version=19`). The command APIs and webhooks carry no version field. `form=2` selects JSON output for command APIs (D/general-faqs).

**Recommendation: implement first** the form-encoded payment response and payment webhook (one parser, since the field sets are the same), plus the Verify Payment JSON. Add the refund webhook, refund API and `check_action_status` JSON next, then the dispute webhook. Leave S2S interim responses, settlement and chargeback APIs for later.

### 3. Response and error formats

#### 3.1 Content type and encoding

- **Payment response to `surl`/`furl`**: "PayU POSTs back to your return URL with URL-encoded fields (form post)" (D/prebuilt-checkout-page-integration). Spaces appear as `+` or `%20` in different samples. The docs also show the same data as a parsed JSON object and as a PHP `print_r` array (`Array ( [mihpayid] => ... )`); these are presentation forms, not wire formats.
- **Payment webhooks (Successful, Failed)**: form POST, URL-encoded ("` application/x-www-form-urlencode`" as printed). The R/webhooks page for Payment Links says the same: `application/x-www-form-urlencoded`.
- **Refund and dispute webhooks**: "Method: POST", "Content type: application/json".
- **Command APIs** (`/merchant/postservice`): request `application/x-www-form-urlencoded` (the Python SDK docs say `multipart/form-data`); response JSON when `?form=2` is present. Without it the FAQ shows a PHP-serialized body such as `a:2:{s:6:"status";i:0;s:3:"msg";s:21:"Merchant key is empty";}`.
- **HTTP status codes**: the command APIs report success and failure inside the body (`status` 1 or 0). HTTP status codes for errors are **NOT DOCUMENTED**. The settlement API documents `code` values `2000`, `4000`, `4001` in the body.
- **Character encoding**: **NOT DOCUMENTED** for responses and webhooks. The hash troubleshooting FAQ mentions "UTF-8 and URL-decoding behaviour for special characters".

### 4. Codes

Code strings are exactly as documented. "Meaning" is a short paraphrase. Category and retry class are **suggestions** for PandaPayLens, not PayU statements; where PayU gives advice (for example "retry after 15 mins"), it is reflected. PayU warns that "the detailing of error reasons may differ from one transaction to another" because reasons come from banks, so an adapter must handle unknown codes and must not rely on a code alone.

**How the code fields relate** (R/error-codes, "Field Error code structure"): `error` / `error_code` holds the PayU code (`E...`), `error_Message` its text, `field7` the execution stage (section 4.7), `field8` the bank's raw reason and `field9` PayU's translation. PayU: "developers should check both" Field7 and the error code. A pending or successful payment can carry `E000`.

**Code spaces overlap.** Numeric refund status codes (`100`-`502`) are not the same space as the issuer response codes (`0`-`99`), and the pre-authorization capture table reuses the refund numbers with different meanings (section 10). The field and the API decide which table applies.

### 5. Lifecycle

#### 5.1 Payment states (R/payment-state-explanations)

| `unmappedstatus` | `status` | Meaning (paraphrase)                                                                  |
| ---------------- | -------- | ------------------------------------------------------------------------------------- |
| `initiated`      | pending  | Customer landed on PayU's page                                                        |
| `in progress`    | pending  | Customer clicked Pay and was routed to the 3DS page                                   |
| `pending`        | pending  | Payment started but not complete; later moves to captured, failed, bounced or dropped |
| `auth`           | success  | Authorized and debited at the bank but not yet captured at PayU (pre-authorization)   |
| `captured`       | success  | Successful                                                                            |
| `userCancelled`  | failure  | Customer cancelled                                                                    |
| `bounced`        | failure  | Customer did not complete (for example never clicked Pay)                             |
| `dropped`        | failure  | PayU got no response from the payment gateway                                         |
| `failed`         | failure  | Failed at the gateway, PayU, issuer or authentication                                 |
| `autoRefund`     | failure  | PayU refunded a payment that turned out successful during reconciliation              |

Spelling varies: the parameter tables list `usercancelled` (lowercase) while the state table and a BNPL sample use `userCancelled`. The S2S interim response uses `metaData.unmappedStatus` (camelCase) and `txnStatus` (`Enrolled` in the sample; other values **NOT DOCUMENTED**).

#### 5.2 Flows that complete later (UPI, net banking, wallets)

- UPI and net banking payments can be `pending` when the browser returns. The guidance is the same on every UPI and net banking page: "Verify the payment using verify\_payment and monitor using webhooks". The general FAQ: do not fulfil while pending, poll Verify Payment with "a bounded retry interval", and raise a support ticket if it stays pending "beyond the normal processing window" (the window length is **NOT DOCUMENTED**). The Payment Links webhook page says PayU "will send a follow-up webhook when the status resolves to `success` or `failure`".
- UPI collect requests can expire (`E4218`); UPI Collect by entering a VPA is sunset by NPCI from 28 February 2026 and, per D/upi-collect-integration, allowed "only on MCC 6012 and 6211"; intent and QR flows replace it.
- Corporate net banking can wait for checker approval (`TXNPENDING`, `VERPENDING`).
- A transaction recorded as failed or dropped can later be found successful during reconciliation and refunded automatically (`autoRefund`, Field7 `AUTOREFUND`). Whether a webhook is sent for that change is **NOT DOCUMENTED**.

#### 5.3 Pre-authorization, capture and cancel

`auth` transactions are captured with `capture_transaction` (`status` 1, `msg` "Capture Request Queued", `request_id`) or cancelled with `cancel_transaction` or `cancel_refund_transaction` ("Cancel Request Queued", `txn_update_id`); a cancel through `cancel_refund_transaction` must be for the full authorized amount. The UPI capture sample returns `result.status` `in progress` with `mode` `UPIOTM` and an `authpayuid`. Final capture state is read with `check_action_status`.

#### 5.4 Refunds

1. `cancel_refund_transaction` with `var1` = `mihpayid`, `var2` = merchant refund token (unique, at most 23 characters), `var3` = amount; full and partial refunds are allowed on `captured`. Response `status` 1 with `msg` "Refund Request Queued" and a PayU `request_id`; `error_code` 102 means queued and counts as success. A capture made the same day gives "Capture is done today, please check for refund status tomorrow".
2. Action states from `check_action_status`: `QUEUED` (accepted, not yet sent to the bank), `SUCCESS`, `FAILURE` ("No funds are deducted for such refunds from the merchant's settlement"). The samples use both upper case (`SUCCESS`) and lower case (`success`).
3. The refund webhook / refund status callback reports `status` `success` or `failure` with `refund_mode` (`Back to Source`, `Instant Credit through UPI`).
4. The bank ARN is "generated within 24-72 business hours of initiating the refund" and arrives in a later "Refund ARN Update" webhook or in the bulk ARN callback.
5. UAT simulation: refund amount 100-200 gives success, 0-99 failure, anything else `in_progress` (R/refund_transaction_api).

#### 5.5 Chargebacks (disputes)

- Types (D/chargeback-types): Chargeback, Pre-arb, Arbitration, Compliance, Good Faith. The webhook example also uses `RBI/BO` and the read API uses `CB`.
- Webhook `cb_status` values (D/webhooks-for-chargeback): New, Pending Response, Pending Doc Review, Submitted to Bank, Insufficient Document, Closed Customer Favour, Closed in Merchant Favour, Closed under Fraud Liability. Both payload examples use `Bank Comm Sent`, which the list does not contain. D/chargeback-status lists a shorter set with `Closed under fraud`.
- Closure reasons (D/chargeback-closure-reasons, 11): No Response, Insufficient doc, Bank Denied to represent, Accepted, Partially Accepted, Offline Refund, Others, Accepted By Riskified, Delivered, Refunded, Partially Refunded.
- Customer reasons (D/chargeback-reasons): 28 free-text reasons such as "Fraud - Card Not Present Environment", "Credit not Processed", "Net-Banking Dispute"; `reason_code` in the webhook carries this text, not a numeric code.
- Money movement: "Upfront-Debit" merchants are debited when a dispute is created, "No-Upfront-Debit" merchants only when it closes in the customer's favour.
- Webhooks are sent when a chargeback is created, when its status changes and when its amount changes.

#### 5.6 Settlement

Verify output includes `Settled_At` and `Merchant_UTR`; action status includes `settlement_id`, `amount_settled`, `UTR_no`, `value_date`. The settlement API lists per-transaction rows with `transactionType` (`capture`, `refund`, `chargeback`, `chargebackreversal`, also `adjustment`, `cancel`) and `settlementStatus` (`Settled`, `Pending`, `On Hold`, `Failed`); refunds and chargebacks have negative `settlementAmount`.

#### 5.7 Subscriptions, payouts, wallets

Mandate and recurring flows (cards SI, e-NACH, UPI Autopay) have their own APIs and webhooks that were not read; the UPI mandate error codes are in 4.1. Payouts and merchant wallets are separate products. **NOT DOCUMENTED** here.

### 6. Notifications (webhooks)

#### 6.1 Delivery

- Events (D/webhook-events-and-sample-payloads): type Payments, events `Successful`, `Failed`, `Refund` (success and failure) and `Dispute`. D/general-faqs still says "Currently, PayU provides two types of webhook events" (success and failure) and lists a Payouts type.
- Configuration: Dashboard (Developers > Webhooks, or Settings > Webhooks in older text), "multiple URLs separated by commas"; per transaction through `partner_webhook_success` / `partner_webhook_failure` (HTTPS, not URL-encoded); or manually by PayU's integration team.
- Source IPs: production `3.7.89.1`, `3.7.89.2`, `3.7.89.3` (DR `52.140.8.88`, `52.140.8.89`, `52.140.8.64`), test `180.179.174.1`, `3.6.73.183`, `3.6.83.44`; D/general-faqs gives a longer, partly different list.
- Acknowledgement: the chargeback troubleshooting section says the endpoint must return 200 OK. Retry schedule, timeout and number of attempts for payment, refund and dispute webhooks are **NOT DOCUMENTED**. (The separate Webhook Alerts monitoring system documents a 5-second timeout and retries on non-200; that system is not the payment webhook.)
- Webhook logs exist in the Dashboard (Developers > Webhook logs).
- Ordering between the browser redirect, the webhook and later webhooks is **NOT DOCUMENTED**. A pending payment is expected to receive a follow-up webhook (Payment Links page only).

#### 6.2 Payload fields

- Payment events: the full payment response vocabulary (section 3.2) as form fields, including `surl`, `curl`, `furl`.
- Refund events: `merchantTxnId`, `mihpayid`, `request_id`, `token`, `amt`, `status`, `action` (`refund`), `refund_mode`, `bank_ref_num`, `bank_arn`, `remark`, `key`, `additionalValue1`, `additionalValue2` (with documented character limits).
- Dispute events: `type` (`payments`), `event` (`dispute`), `reason_code`, `created_at`, `updated_at` (ISO 8601 with `+05:30`), `mid`, `cb_id` (number), `txn_id` (PayU transaction ID), `cb_type`, `due_date`, `cb_amount` (string), `cb_status`.
- Refund ARN callback (bulk): top-level keys are merchant transaction IDs, each with an array of `PayuID`, `RequestID`, `RefundToken`, `PaymentGateway`, `Amount`, `Status`, `RefundCreationDate`, `bank_ref_no`, `bank_arn`, `success_at`, `BaseTxnID`.

#### 6.3 Signature fields (sensitive; PandaPayLens does not verify them)

- Payment response and payment webhook: `hash` = SHA-512 (128 hex) of the reverse sequence `SALT|status||||||udf5|udf4|udf3|udf2|udf1|email|firstname|productinfo|amount|txnid|key`, with `additional_charges|` prepended and/or `splitInfo` after `status` when used (D/hashing-request-and-response). Payment Links webhooks use `client_secret` instead of the salt.
- Dispute webhook (optional, enabled by PayU support): headers `X-PayU-Dispute-Webhook-Signature-V1`, `X-PayU-Dispute-Webhook-Signature-V2`, `X-PayU-Dispute-Webhook-Signature-Algorithm` (`SHA512`). Signed string `merchantKey|txn_id|cb_amount|cb_id|cb_type|cb_status|merchantSalt`, where `cb_status` is a "mapped" value (`Pending Response` signed as `PendingResponse`). Aggregator child merchants are signed with the parent's key and salt.
- Refund webhooks and the ARN callback: no signature field is documented (**NOT DOCUMENTED**).
- Command API requests carry `hash` = `sha512(key|command|var1|salt)`; settlement APIs use an HMAC `authorization` header with a `date` header.

#### 6.4 Duplicate identification

- No event or delivery ID exists in any payment, refund or dispute webhook. D/general-faqs: "Validate the hash in every payload and handle duplicate events idempotently."
- Suggested dedupe keys: payment events `mihpayid` + `status` + `unmappedstatus`; refund events `request_id` + `status` + `bank_arn` (the ARN update repeats the refund with a new `bank_arn`); dispute events `cb_id` + `cb_status` + `cb_amount` + `updated_at`. `EX213` ("Duplicate Callback") suggests PayU itself detects duplicate callbacks in some flows.
- Merchant-side idempotency: `txnid` must be unique (`EX108`, `E504`); refund `token` must be unique (`106`, `227`); two refunds of the same amount within 5 minutes are refused (`214`).

### 9. Structural detection hints

Strong PayU India signals (combine several):

1. **Payment response / webhook (form-encoded)**: `mihpayid` together with `txnid`, `status` in {`success`, `failure`, `pending`}, `unmappedstatus`, `error` matching `^E\d{3,4}$` (or `E000`), `error_Message` (capital M), `PG_TYPE` ending in `-PG`, `field0`-`field9`, `udf1`-`udf10`, `payment_source`, and a 128-hex `hash`. `mihpayid` + `unmappedstatus` is decisive; no supported provider uses either name.
2. **Verify Payment JSON**: integer `status` 0/1 + `msg` matching `^\d+ out of \d+ Transactions Fetched Successfully$` + `transaction_details` object keyed by merchant IDs, values with `mihpayid` (possibly `"Not Found"`), `unmappedstatus`, `error_code`, `PG_TYPE`.
3. **Transaction details JSON**: `Transaction_details` array with `id`, `ibibo_code`, `bank_ref_no`, `merchantname`, `payment_gateway` (`AXISPG`), `mer_service_fee`, `mer_service_tax`.
4. **Refund webhook JSON**: `merchantTxnId` + `mihpayid` + `request_id` + `token` + `action: "refund"` + `refund_mode` + `additionalValue1`/`additionalValue2`. **ARN callback**: objects with `PayuID`, `RequestID`, `RefundToken`, `PaymentGateway`, `BaseTxnID`.
5. **Dispute webhook JSON**: `type: "payments"`, `event: "dispute"` with `cb_id`, `cb_type`, `cb_status`, `cb_amount`, `txn_id`, `mid`, timestamps with `+05:30`; headers `X-PayU-Dispute-Webhook-Signature-V1/V2`.
6. **S2S JSON**: `metaData` {`referenceId`, `txnId`, `txnStatus`, `unmappedStatus`} with `result` and `binData` {`pureS2SSupported`, `issuingBank`, `isDomestic`}.
7. **Command API envelope**: `status` 0/1 + `msg` and optionally `request_id`, `txn_update_id`, `error_code` 102; PHP-serialized bodies starting `a:2:{s:6:"status"`.
8. **Hosts and paths**: `secure.payu.in/_payment`, `test.payu.in/_payment`, `info.payu.in/merchant/postservice.php?form=2`, `apitest.payu.in/settlement/...`, `onboarding.payu.in`; Field7 values such as `AUTHPOSITIVE`, `AUCNEGATIVE`, `TXNPENDING`.

How this differs from supported providers:

- **Stripe, Adyen, Checkout.com, PayPal, Braintree, Mollie, Square, Worldpay, Authorize.net**: JSON (or XML) envelopes with their own keys (`object` and `evt_` IDs; `pspReference` and `notificationItems`; `event_type` with `resource`; `eventId` with `eventDetails`; `transactionResponse` with `transId`) as described in their research files. None use `mihpayid`, `unmappedstatus` or a form-encoded body with `field0`-`field9`.
- **Cybersource**: JSON with `errorInformation` (cybersource research file); PayU uses `error` / `error_Message`.
- **payabl.**: also URL-encoded, but with `transactionid`/`transid`, `errormessage`/`errmsg` and `security` (payabl. research file). PayU uses `txnid`, `mihpayid`, `error_Message`, `hash`.
- **NMI**: lowercase `response`, `responsetext`, `authcode`, `transactionid`, `response_code` (nmi research file). PayU's `status` is a word and its IDs are `mihpayid` / `txnid`.
- **Nuvei**: DMNs with `ppp_status`, `PPP_TransactionID`, `ErrCode`, `advanceResponseChecksum`; REST JSON with `internalRequestId` and `gwErrorCode`.
- **Form-posting high-risk adapters**: CCBill (`clientAccnum` + `clientSubacc`), Segpay (`purchaseid` + `eticketid`), Verotel (`saleID` + `shopID` + `signature`), NETbilling (`status_code` + `trans_id`, `Ecom_Ezic_`), Skrill (`mb_transaction_id` + `md5sig`), Paymentwall (`uid`, `ref`, `sig`), emerchantpay (`unique_id` + `terminal_token` + `signature`), per their research files. None overlap with PayU's key set.
- **Generic names**: `status`, `key`, `amount`, `hash`, `mode`, `txnid`, `email`, `phone` are common elsewhere and must not decide alone. `status=success|failure` without `mihpayid` is not enough.
- **PayU in other regions**: other PayU platforms share the brand but not this format; they were not researched, so their formats are **NOT DOCUMENTED** here. Detection should name this format "PayU India" only on the PayU India field set or `*.payu.in` hosts, never on the word "PayU" alone.
- **Routed transactions**: `pa_name` can name another aggregator (the docs' example is RazorPay). The payload is still PayU India's format and belongs to this adapter.

### 10. Limitations, ambiguities and documentation inconsistencies

1. **UPI error table contradicts the main table**: for 67 of its 210 rows the UPI table gives a different reason than the main payment table for the same code (for example `E000` "Error at the Bank Server end", `E1206` "Invalid Merchant Key" vs. "back button", `E700` 3DS enrolment decline vs. hash validation). The rows look shifted. The main table is used in 4.1; the UPI table should not drive decoding.
2. **Same code, different texts**: `E307`, `E9251`, `E9252`, `E9254` have two rows each in the main table; `EX151`, `EX306`, `EX307`, `EX401` likewise. The issuer table maps response `91` to two codes and maps `86` ("Cannot verify PIN") to `E4519`, a refund code.
3. **Codes used in examples but missing from tables**: `E4936` (Verify Payment example), `E756` exists only in an accordion on the error page. The AuthN/AuthZ tables carry 13 codes with no message and non-code values (`01`, `400`, `failed`, empty).
4. **Generic texts**: `E4888`-`E4910` all say "FAILURE"; `E4931` contains the template placeholder `` `value` ``; many `EX` rows are internal platform errors with `?` placeholders or titles only.
5. **Field name drift**: `error_Message` (all samples) vs `error_message` (tables); `mihpayupid` (verify table) vs `mihpayid` (samples); `bank_ref_num` vs `bank_ref_no` (both sent in webhooks); `additionalCharges` vs `additional_charges`; `authenticaticationMethod` vs `authenticationMethod`; `unmappedStatus` vs `unmappedstatus`; `usercancelled` vs `userCancelled`; refund action status `SUCCESS` vs `success`; `transaction_details` vs `Transaction_details` vs `Refund Details`.
6. **Status value drift**: R/addl_info-payment-apis lists `success`, `failed` or `pending` in one table and `failure` in another; all samples use `failure`.
7. **Webhook event list conflicts**: four events on D/webhook-events-and-sample-payloads, "two types" on D/general-faqs; neither lists a pending event, while the Payment Links page promises follow-up webhooks for pending payments.
8. **Dispute vocabulary conflicts**: both dispute examples use `cb_status` `Bank Comm Sent`, which is not in the documented list; `cb_type` `RBI/BO` and `CB` are not in the types list; D/chargeback-status and the webhook page list different status sets.
9. **Refund codes reused**: the capture table assigns `101` to success and `100` to "capture in successful state", while the refund table assigns `100` to success and `101` to pending. `109` means "Request is already logged" for refunds and "Capture failed" for captures.
10. **Example quality**: the hosted checkout raw response and its "parsed" JSON differ (other hash, `field1`-`field9` values, `firstname`); the Verify Payment parameter table lists refund-style fields (`action`, `token`, `bank_arn`) that the verify samples do not contain; R/check_payment_api shows `status: 1` together with "Not Found"; the verify "Offer availed at Transaction level" sample embeds unescaped JSON inside a string (invalid JSON); refund API examples are PHP `print_r` output; one hosted checkout UPI sample mixes `&"phone":"##########"&` JSON syntax into a form string; R/_payment_s2s_upi_collection shows a card-style `pares` response for UPI.
11. **`error_code` 102** is called success on the refund page but the generic "Error Codes" link on the same page points to the payment error list, not the refund list.
12. **Settlement API inverts `status`**: 0 = success and 1 = failure, the opposite of the command APIs.
13. **Missing delivery semantics**: no webhook event ID, retry policy, timeout or ordering rule; no response time zone (samples look like Indian Standard Time; dispute timestamps carry `+05:30`).
14. **Hash formulas vary**: request hash differs for `api_version=19` and for standing-instruction registrations; reverse hash has four variants; the Node SDK reverse-hash comment omits `udf1`-`udf4` positions. PandaPayLens does not verify hashes, so this only matters for documentation links.
15. **Data source of code tables**: the Error Codes page renders its tables from JSON in a GitHub repository under a personal account (`palgunams21/payu-docs-assets`), not an organisation account. The content is what docs.payu.in displays, but it can change without a page update.
16. **Test environment gaps**: R/introduction-api-reference says many flows (UPI, refunds, collect payments, S2S UPI) cannot be tried in the API reference test console.
17. **Not read**: subscriptions and their webhooks, payouts, offers, BNPL, QR, wallets and cross-border pages; PayU platforms outside India.

### 11. Proposed capability statuses

| Capability           | Proposed      | Justification                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------------------- | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **errorDecoding**    | **supported** | Over 900 first-party gateway codes plus Field7 stages, refund codes and the issuer mapping, all in public tables, with a documented structure (`error`, `field7`, `field8`, `field9`). Raw bank texts in `field8` vary by bank and are shown as-is                                                                      |
| **paymentResponses** | **supported** | The form-encoded payment response and the Verify Payment JSON have parameter tables and many samples across cards, UPI, net banking, wallets and BNPL with a stable core (`mihpayid`, `txnid`, `status`, `unmappedstatus`, `error`, `error_Message`, `bank_ref_num`). Spelling drift is easy to tolerate. S2S interim responses and settlement output would start as `limited`                                                                                  |
| **webhookParsing**   | **limited**   | Payment, refund and dispute payloads are documented with samples and field tables, but there is no event ID, no retry or ordering rule, the event list conflicts between pages, dispute status values in examples are not in the list, and refund webhooks have no signature field                                                                                                                                                                              |
