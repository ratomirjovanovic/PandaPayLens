# PayPal provider research (adapter id `paypal`)

> Research notes for a **parse-only** PandaPayLens adapter. The adapter never calls PayPal.
> Everything below comes from PayPal's official developer documentation (developer.paypal.com),
> including the official OpenAPI specs that the reference pages link to. Where the docs are silent,
> this file says **NOT DOCUMENTED**. The category and retry columns are **PandaPayLens proposals**
> based on PayPal's wording. PayPal does not publish them.

## 3. Error response format

### 3.1 Schema (S6 and S8, identical in both specs)

`error` object:

| Field      | Type                      | Spec description                                         |
| ---------- | ------------------------- | -------------------------------------------------------- |
| `name`     | string                    | "The human-readable, unique name of the error."          |
| `message`  | string                    | "The message that describes the error."                  |
| `debug_id` | string                    | "The PayPal internal ID. Used for correlation purposes." |
| `details`  | array of `error_details`  | "An array of additional details about the error."        |
| `links`    | array of link_description | HATEOAS links (readOnly)                                 |

`error_details` object ("Required for client-side `4XX` errors."):

| Field         | Spec description                                                                                                                                    |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `field`       | "The field that caused the error. If this field is in the body, set this value to the field's JSON pointer value. Required for client-side errors." |
| `value`       | "The value of the field that caused the error."                                                                                                     |
| `location`    | "Value is `body`, `path`, or `query`." Default `body`.                                                                                              |
| `issue`       | "The unique, fine-grained application-level error code."                                                                                            |
| `description` | "The description can change over the lifetime of an API, so clients must not depend on this value."                                                 |
| `links`       | 1-4 HATEOAS links relevant to the issue                                                                                                             |

Notes for the parser:

- S2: "The fields returned in the details array vary by error." `field`, `value` and `location` are often absent (see example 3.4).
- The JSON key order is **not stable**. In S3, `details` sometimes comes before `message`.
- Link objects carry `href`, `rel` and an optional `method` (S2: "If absent, the default method is GET"). Observed `rel` values in errors: `information_link` and `payer-action` (S6 capture 422 example).
- **`name` is not always spelled consistently in PayPal's own examples.** S8 has several 422 examples with `"name": "UNPROCCESSABLE_ENTITY"` (double C). One example is the refund `REFUND_AMOUNT_EXCEEDED` example below. Other 422 examples in the same spec use `UNPROCESSABLE_ENTITY`. The adapter should accept both spellings.
- S2's generic template is **not valid JSON**: one `links` entry is a bare string, `{"https://error_documentation_link", "rel": ...}`. Don't use it as a fixture.
- **Identity (OAuth) errors use another shape** (S2): `{"error": "ERROR_NAME", "error_description": "ERROR_DESCRIPTION"}`, for example `{"error": "invalid_client", "error_description": "Client Authentication failed"}` with HTTP 401.
- S3 mentions a `correlation_id` in a **response header**. The header name and format are NOT DOCUMENTED in the pages read. The `debug_id` in the body is the documented correlation id.

### 3.2 HTTP status codes

From S2 (generic) and S3 (Orders v2):

| HTTP | `name`                                                                                   | Meaning (paraphrased)                                                                                                                                             |
| ---- | ---------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 200  | -                                                                                        | Success. Also returned when a repeated POST with an already-processed `PayPal-Request-Id` gets the stored result.                                                 |
| 201  | -                                                                                        | Resource created                                                                                                                                                  |
| 202  | -                                                                                        | Accepted for later processing. Orders capture can return 202, which S6 calls "handled asynchronously".                                                            |
| 204  | -                                                                                        | Success, no body                                                                                                                                                  |
| 207  | -                                                                                        | Orders capture only (S6): multiple purchase units with mixed outcomes                                                                                             |
| 400  | `INVALID_REQUEST`                                                                        | Malformed, or fails schema validation. Also used for several OAuth errors.                                                                                        |
| 401  | `AUTHENTICATION_FAILURE` (REST, S3/S1); `INVALID_CLIENT`, `INVALID_TOKEN`, … (OAuth, S2) | Missing or invalid credentials                                                                                                                                    |
| 403  | `NOT_AUTHORIZED`                                                                         | Valid credentials but insufficient permissions or scope. S2 adds that "a business-level authorization error might have occurred", for example insufficient funds. |
| 404  | `RESOURCE_NOT_FOUND`                                                                     | Unknown resource or URI                                                                                                                                           |
| 405  | `METHOD_NOT_SUPPORTED`                                                                   | HTTP method not supported                                                                                                                                         |
| 406  | `MEDIA_TYPE_NOT_ACCEPTABLE`                                                              | `Accept` type not producible                                                                                                                                      |
| 409  | `RESOURCE_CONFLICT`                                                                      | Conflicts with a request in progress. "Retry the request later."                                                                                                  |
| 415  | `UNSUPPORTED_MEDIA_TYPE`                                                                 | Request `Content-Type` not supported                                                                                                                              |
| 422  | `UNPROCESSABLE_ENTITY`                                                                   | Semantically incorrect or fails business validation. **Most payment declines land here.**                                                                         |
| 429  | `RATE_LIMIT_REACHED`                                                                     | "Too many requests. Blocked due to rate limiting."                                                                                                                |
| 500  | `INTERNAL_SERVER_ERROR`                                                                  | Unexpected server error                                                                                                                                           |
| 503  | `SERVICE_UNAVAILABLE`                                                                    | Temporary maintenance                                                                                                                                             |

S2 note, quoted: "An HTTP 5xx or network timeout from an /execute or /capture endpoint could have resulted in the creation of a PayPal transaction. To be informed of the transaction, it is recommended that you repeat the same /execute or /capture call at least once, with the same PayPal-Request-Id HTTP header as before."

OAuth-specific names (S2), for detection only: `INVALID_CLIENT`, `INVALID_AUTHZ_CODE`, `INVALID_REDIRECT_URI`, `INVALID_TOKEN`, `UNAUTHORIZED_CLIENT`, `UNSUPPORTED_GRANT_TYPE`, `INVALID_RESPONSE_TYPE`, `INVALID_USER`, `RISK_DECLINE`, `REMEMBER_ME_EXPIRED`.

| `AUTHENTICATION_FAILURE`                              | 401  | configuration                                   | do_not_retry                                                                    | S1/S3: missing auth header or invalid credentials. This is API credentials, not a 3DS failure. |
| `NOT_AUTHORIZED`                                      | 403  | configuration                                   | do_not_retry                                                                    | S2: insufficient permissions or scope                                                          |
| `RESOURCE_NOT_FOUND`                                  | 404  | invalid_request                                 | do_not_retry                                                                    | S2                                                                                             |
| `METHOD_NOT_SUPPORTED`                                | 405  | invalid_request                                 | do_not_retry                                                                    | S2                                                                                             |
| `MEDIA_TYPE_NOT_ACCEPTABLE`                           | 406  | invalid_request                                 | do_not_retry                                                                    | S2                                                                                             |
| `RESOURCE_CONFLICT`                                   | 409  | duplicate_request                               | retry_conditionally                                                             | S2: "Retry the request later."                                                                 |
| `UNSUPPORTED_MEDIA_TYPE`                              | 415  | invalid_request                                 | do_not_retry                                                                    | S2                                                                                             |

| `SERVICE_UNAVAILABLE`                                 | 503  | provider_unavailable                            | retry_conditionally                                                             | S2                                                                                             |

**Decoding rule:** for 4xx, the decisive code is `details[0].issue`. `name` only identifies the class of error. `details` can hold more than one entry. The docs do not state an ordering or priority for multiple entries, so treat it as NOT DOCUMENTED.

**`avs_code`** (24 values). Visa/MC/Discover/Amex letters: `A B C D E F G I M N P R S U W X Y Z`. Maestro digits: `0 1 2 3 4` and `Null`. S16 meanings, examples: `M` address and postal match, `N` nothing matches (declined), `G` global unavailable, `U` unavailable, `R` retry, `S` service not supported, `Y` address and 5-digit ZIP, `X` exact match (address and 9-digit ZIP), `Z` 5-digit ZIP only. **`cvv_code`** (14 values). `E` error, `I` invalid or null, `M` match, `N` no match, `P` not processed, `S` not supported, `U` issuer not certified, `X` no response, "All others" error. Maestro: `0` matched, `1` no match, `2` merchant has not implemented, `3` not present on card, `4` unavailable.

**`payment_advice_code`** (15 values: `01 02 03 04 21 22 24 25 26 27 28 29 30 40 43`). These are network advice codes. Examples from S9: `02` (Mastercard: over limit or insufficient funds, retry after 72 hours; Visa: stop this one recurring payment, do not resubmit), `03` (Mastercard: account closed as fraudulent; Visa: stop all recurring payments), `21` (stop recurring), `24`-`30` (Mastercard: retry after 1 hour / 24 hours / 2, 4, 6, 8, 10 days). These map naturally to `retry_conditionally` or `do_not_retry`.

**Emphasis for the adapter and the UI:**

- **`APPROVED` ≠ captured.** Approval means only that the buyer consented. No money has moved. S19: on `CHECKOUT.ORDER.APPROVED`, "Listen for this webhook and then capture the payment." S18: if the order is not captured within the window (default 3 hours for the APMs described there), PayPal sends `CHECKOUT.PAYMENT-APPROVAL.REVERSED`, cancels the order and refunds the buyer.
- **`COMPLETED` ≠ paid.** S17 shows an official response with order `"status": "COMPLETED"` and capture `"status": "DECLINED"`, with `processor_response.response_code` `5400`. Outcome must come from the capture or authorization status, never from the order status.
- With `intent=AUTHORIZE`, a `COMPLETED` order means an authorization exists. Funds are not captured until a Payments v2 capture happens.

### 5.2 Authorization status (`authorization_status`)

`CREATED` (no captures yet), `CAPTURED` (one or more captures; S10's wording says their sum "is greater than the amount of the original authorized payment"), `DENIED` (PayPal cannot authorize), `PARTIALLY_CAPTURED`, `VOIDED` (no further captures), `PENDING` (see `status_details`).
`status_details.reason`: `PENDING_REVIEW` (manual review), `DECLINED_BY_RISK_FRAUD_FILTERS` (payee's risk filter failed).
Other fields: `expiration_time` (the spec gives no description), `create_time`, `update_time`.
S11: `PAYMENT.AUTHORIZATION.VOIDED` fires when the authorization reaches its 30-day validity or is voided manually. S3: if the authorization is older than 3 days, reauthorize before capturing. S8: reauthorization is allowed once, from day 4 to day 29.

### 5.3 Capture status (`capture_status`)

| Status               | S10 meaning                                  |
| -------------------- | -------------------------------------------- |
| `COMPLETED`          | Funds credited to the payee's PayPal account |
| `DECLINED`           | Funds could not be captured                  |
| `PARTIALLY_REFUNDED` | Less than the captured amount was refunded   |
| `PENDING`            | Not yet credited. See `status_details`.      |
| `REFUNDED`           | An amount ≥ the captured amount was refunded |
| `FAILED`             | An error occurred while capturing            |

`status_details.reason` ("why the captured payment status is `PENDING` or `DENIED`". The spec says DENIED although the status enum is `DECLINED`.):
`BUYER_COMPLAINT`, `CHARGEBACK`, `ECHECK` (eCheck not cleared), `INTERNATIONAL_WITHDRAWAL`, `OTHER`, `PENDING_REVIEW`, `RECEIVING_PREFERENCE_MANDATES_MANUAL_ACTION` (for example a currency the payee doesn't hold), `REFUNDED`, `TRANSACTION_APPROVED_AWAITING_FUNDING` (manual EFT), `UNILATERAL` (payee has no PayPal account), `VERIFICATION_REQUIRED` (payee not verified), `DECLINED_BY_RISK_FRAUD_FILTERS`.

S19: on `PAYMENT.CAPTURE.PENDING`, "Do not fulfill the order until payment completion is successful."

### 5.4 Refund status (`refund_status`)

`CANCELLED`, `FAILED`, `PENDING`, `COMPLETED` ("funds … debited to the customer's account"; the wording is PayPal's). `status_details.reason`: `ECHECK` only.

### 6.3 Delivery, duplicates and ordering

- Delivery (S12/S13): the listener must return 2xx. Otherwise PayPal "will reattempt delivery up to 25 times over the course of 3 days". After that the delivery is marked Failed and can be resent manually from the dashboard or with the `resend` link.
- **Duplicates:** NOT DOCUMENTED explicitly. Retries and manual resends make re-delivery of the same event possible. Deduplicate on envelope `id`. Each delivery also has a `PAYPAL-TRANSMISSION-ID` header, but headers are usually not part of a pasted payload.
- **Ordering:** NOT DOCUMENTED. No ordering guarantee is stated, so the timeline must sort by `create_time` (envelope) and/or `resource.update_time`/`create_time`, and must cope with, for example, `PAYMENT.CAPTURE.COMPLETED` arriving before `CHECKOUT.ORDER.APPROVED`.
- **Mock events** from the Webhooks simulator use the webhook id string `WEBHOOK_ID` (S13).

### 6.4 Verification headers (sensitive; the adapter never verifies)

From S13 and S14: `PAYPAL-TRANSMISSION-ID`, `PAYPAL-TRANSMISSION-TIME`, `PAYPAL-TRANSMISSION-SIG` (base64 asymmetric signature), `PAYPAL-CERT-URL` (X.509 cert URL), `PAYPAL-AUTH-ALGO` (for example `SHA256withRSA`). The signed string is `transmissionId|timeStamp|webhookId|crc32(rawBody)` (CRC32 in decimal), checked against the cert's public key with SHA256. Verification requires the **raw body**: "do not parse the body to an array/object and then re-stringify it". The postback alternative is `POST /v1/notifications/verify-webhook-signature`, which returns `verification_status` of `SUCCESS` or `FAILURE`. The S13 sample listener also logs a `correlation-id` header.

If a user pastes these headers, or a `verify-webhook-signature` request body, the adapter should redact `transmission_sig`/`PAYPAL-TRANSMISSION-SIG` and `webhook_id`, and should never display `cert_url` as a link. A pasted payload alone can never be proven authentic, and the UI should say so.

**Linking capture → order:**

1. Primary: `resource.supplementary_data.related_ids.order_id` on Payments v2 capture, authorization or refund resources. `related_ids` also has `authorization_id` and `capture_id`, so a refund can point to its capture and a capture can point to its authorization.

## 8. Sensitive fields

Redact or mask before display or storage (from the S6/S8 schemas and samples):

- **Payer identity:** `payer.email_address`, `payer.name.given_name`/`surname`, `payer.phone`, `payer.birth_date`, `payer.tax_info` (tax id), `payer.address.*`, `payer.payer_id`.
- **Wallet:** `payment_source.paypal.email_address`, `.name`, `.phone_number`, `.birth_date`, `.tax_info`, `.address`, `.account_id`, `.business_name`. The same applies to `venmo` and other APM blocks (`ideal.name`, `blik`, `p24`, …, which hold payer names, e-mails and IBAN-like data).
- **Card:** `payment_source.card.name`, `.billing_address`, `.expiry`, `.last_digits` (low risk, but mask), `.bin_details`, `authentication_result` (3DS data). Request-side cards may carry `number` and `security_code`. If a pasted _request_ contains them, reject or redact aggressively. Errors may echo `details[].value`, which can contain the offending field value (for example a card number or postal code). **Always redact `details[].value`.**
- **Shipping:** `purchase_units[].shipping.name`, `.address.*`, `.email_address`, `.phone_number`.
- **Payee / merchant:** `payee.email_address`, `payee.merchant_id` (lower risk, but personal for sole traders).
- **Refund:** `refund.payer` (email/merchant id), `note_to_payer` (free text).
- **Free text:** `purchase_units[].description`, `soft_descriptor`, `items[].name/description`, `custom_id`/`invoice_id` (merchants sometimes put e-mails or order numbers here).
- **Secrets that may be pasted by mistake:** `Authorization: Bearer …` access tokens (S6 x-samples include them in request headers), webhook verification headers (§6.4), `webhook_id`, client id or secret.
- **Links:** `approve` and `payer-action` URLs carry the order token.

## 9. Structural detection hints (vs Stripe, Adyen, Checkout.com)

PayPal signals (score them; don't rely on a single one):

- **Webhook:** top-level `event_type` matching `^[A-Z][A-Z0-9_-]*(\.[A-Z0-9_-]+)+$` (uppercase dotted, for example `PAYMENT.CAPTURE.COMPLETED`), plus `resource` (object) and `summary`/`create_time`. Optional `id` starting `WH-`, `resource_type`, `resource_version`/`event_version` like `"2.0"`/`"1.0"`, and `links[].href` on `api.paypal.com`, `api-m.paypal.com`, `api.sandbox.paypal.com` or `api-m.sandbox.paypal.com`.
  - _Stripe:_ `"object": "event"`, lowercase dotted `type` (`payment_intent.succeeded`), `id` `evt_…`, `data.object`.
  - _Adyen:_ `notificationItems[].NotificationRequestItem`, `eventCode` (`AUTHORISATION`), `pspReference`, `"live": "false"` string.
  - _Checkout.com:_ lowercase `type` with underscores (`payment_captured`), `data`, ids `evt_`/`pay_`. No `resource`.
- **Error body:** `name` (UPPER_SNAKE) + `message` + `debug_id` (+ `details[].issue`, `links[].rel == "information_link"`, `href` to developer.paypal.com). `debug_id` is the strongest discriminator.
  - _Stripe:_ `{"error": {"type", "code", "decline_code", "message", "request_id"?}}`.
  - _Adyen:_ `status`, `errorCode` (numeric string), `errorType`, `pspReference`.
  - _Checkout.com:_ `request_id`, `error_type`, `error_codes[]`.
  - _PayPal OAuth:_ `{error, error_description}`. This overlaps with generic OAuth shapes, so give it low confidence unless the context says PayPal.
- **Order response:** `intent` ∈ {`CAPTURE`,`AUTHORIZE`}, `purchase_units[]`, `status` ∈ order enum, `links[].rel` ∈ {`self`,`approve`,`payer-action`,`capture`,`authorize`,`update`}.
- **Capture/authorization resource:** `seller_receivable_breakdown`, `seller_protection`, `final_capture`, `supplementary_data.related_ids`, amounts as `{currency_code, value: "10.00"}`. The **string** decimal `value` contrasts with Stripe and Adyen integer minor units and with Checkout.com's integer `amount`.

## 10. Limitations

1. **No per-issue HTTP status in S1.** S1 groups issues by `name`. The HTTP status comes from the `name` → status table (S2/S3).
2. **No Payments v2 error page.** The 107 Payments v2 issues come only from the spec's `x-errors` (`name`/`message`/`description`), and that list is not tied to endpoints. A few names repeat with different text (for example `TRANSACTION_REFUSED`).
3. **PayPal's own examples have inconsistencies:** the `UNPROCCESSABLE_ENTITY` typo, invalid JSON in the S2 template and the S18 webhook sample, and `PAYMENT.CAPTURE.DECLINED` vs `PAYMENT.CAPTURE.DENIED`.
4. **Webhook duplicates and ordering are NOT DOCUMENTED** beyond "up to 25 retries over 3 days".
5. **`resource_type` values are NOT DOCUMENTED** (only `capture` is seen in samples). There is no official `CHECKOUT.ORDER.APPROVED` payload sample in the pages read.
6. **Sample payloads for `PAYMENT.CAPTURE.REFUNDED` and `PAYMENT.CAPTURE.REVERSED` (whether the resource is a refund or a capture) are NOT DOCUMENTED.**
7. **`processor_response.response_code` meanings are one-word tokens.** Only a few codes have guidance ("Do not retry the same card", "Retry"). The categories here are inference.
8. **Signature verification is impossible offline** without the raw body, the headers, the webhook id and the cert. A parse-only tool cannot authenticate payloads.
9. **Subscriptions, Disputes, Payouts, Vault, legacy v1 (`PAY-…`, `sale`) and NVP/SOAP are out of scope.** Their events would only be labelled.
10. **Multi-purchase-unit orders** (207 Multi-Status, `DECLINED_DUE_TO_RELATED_TXN`) can mix outcomes. The timeline must be per purchase unit or capture.
11. Descriptions "can change over the lifetime of an API, so clients must not depend on this value" (S6). Decode on `issue` only.
12. The response header carrying `correlation_id`/`Paypal-Debug-Id` is NOT DOCUMENTED in the pages read.
