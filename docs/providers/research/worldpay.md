# Worldpay (adapter id `worldpay`): provider research

Status: research notes for building a parse-only PandaPayLens adapter. Nothing here is a guarantee about live behavior. Everything comes from Worldpay's first-party documentation, its published OpenAPI files, its published DTD and its official SDK repositories as read on the verification date. When a point is not documented, the text says **NOT DOCUMENTED**. Nothing was logged into, signed up for or requested.

- Verification date: **2026-10-25**
- Gate outcome: **documentation_verified** (for the Access Worldpay JSON family; see the qualification gate)
- Method: Access Worldpay pages were downloaded as raw Markdown (`https://docs.worldpay.com/access/products/<path>.md`, the format listed in the site's own `llms.txt` index), and the five OpenAPI bundles linked from the API reference pages were downloaded as YAML and read. The pages under `https://docs.worldpay.com/apis/` (WPG, cnpAPI, Event Notifications) are rendered client-side; their text was read from the `index.md` variant the site serves for each page (`https://docs.worldpay.com/apis/<path>/index.md`). In that variant, tables are flattened into text and XML examples are stripped, so XML examples for those families could not be transcribed. "Last updated" values are the pages' own header dates.

## Classification and documented sectors

| Class                        | Evidence                                                                                                                                                                                                                                                                |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `acquiring`                  | Raw codes come "from the card scheme (for Worldpay-acquired transactions)" or "a third party acquirer" (refusal-response page). WPG extended codes apply "if Worldpay is your acquirer" (useful tables). WPG M/R/S service levels handle settlement and reconciliation. |
| `gateway`                    | WPG is the "Worldwide Payment Gateway"; at C-level "The Worldwide Payment Gateway handles the authorisation and capture of your payments. Your acquirer handles settlement and reconciliation."                                                                         |
| `card_processing`            | Card Payments v7 and Payments API authorize, settle, refund and reverse card payments; cnpAPI is a card-not-present processing format with Online and Batch submission.                                                                                                 |
| `alternative_payment_method` | APMs API covers eWallets, bank transfers, direct debits, BNPL (Klarna, PayPal, iDEAL, Pix, SEPA DD, Swish and others on the APM manage page).                                                                                                                           |

Not assigned: `orchestration` (Worldpay uses "Orchestrated" for its own Payments API that wraps its FraudSight, 3DS and token modules; it is not multi-provider orchestration), `wallet` (Apple Pay and Google Pay are accepted, not operated), `payment_facilitator` (Worldpay documents features for merchants that are payment facilitators; it does not describe itself as one), `merchant_account_intermediary`.

Sectors: see gate item 6. Worldpay documents data rules for financial services (MCC 6012/6051, Visa Europe), crypto ramp providers, airline/lodging/purchasing Level 2/3 data and Latin America installments, and mentions gambling in a refusal-code footnote. Approval for one sector does not imply another.

## 3. Response and error formats

### 3.1 Content types and HTTP status

- **JSON everywhere in Access Worldpay.** Payments API and APMs: `application/json` plus `WP-Api-Version`. Card Payments v7: `application/vnd.worldpay.payments-v7+json`. Payment Queries: `application/vnd.worldpay.payment-queries-v1.hal+json`. Events: `application/vnd.worldpay.events-v1.hal+json`.
- **HTTP status** (Payments API OpenAPI): `201` for `authorized`, `refused`, `3dsDeviceDataRequired`, `fraudHighRisk`; `202` for `sentForSettlement` and `sentForCancellation`. Settle, refund, cancel and reversal requests answer `202` "which confirms we have received your request. The request has not processed at this stage" (Card Payments manage page).
- **Errors**: 4xx means the request must be fixed, then "you can safely retry"; 5xx are server-side, "The most common example of 5xx errors are timeouts" (error responses page). The page says the HTTP status and top-level `errorName` are "the most reliable elements" for automated decisions; `message` "can't be relied upon to remain stable".
- **Response header**: `WP-CorrelationId` on every response (API principles). It is not in the body, so it appears only when headers are pasted.
- Responses can add new fields, new enum values, new links and new error names without a version change (API principles, "non-breaking changes"). A parser must ignore unknown fields.

### 3.2 Field names

**Error envelope** (all Access APIs):

| Field                | Type   | Meaning                                                                                                              |

**Card Payments v7 response** (schemas `payments_authorize_201_response`, `payments_authorize_201_refusal`): `outcome`, `paymentId`, `commandId`, `refusalCode`, `gatewayRefusalCode` ("Extended refusal code generated by us, returned only for merchants configured to receive raw scheme response codes in the `refusalCode` field"), `refusalDescription`, `advice.code`, `riskFactors`, `exemption`, `issuer.authorizationCode`, `scheme.reference`, `scheme.supplementaryReference`, `paymentInstrument`, `updatedPaymentInstrument`, `amounts` (`requested`, `totalAuthorized`, `currency`, `partialAuthorization`), `_links` (`cardPayments:cancel`, `cardPayments:partialCancel`, `cardPayments:settle`, `cardPayments:partialSettle`, `cardPayments:events`, `cardPayments:reverse`, `curies`). It has **no** `transactionReference` in the response schema.

**Raw codes vs Worldpay codes.** `refusalCode` carries the Worldpay code (section 4.1) by default. If the merchant is configured for raw codes, `refusalCode` carries the raw scheme or acquirer code (section 4.3, "a string of up to 20 characters") and, in Card Payments v7 only, `gatewayRefusalCode` carries the Worldpay code. The Payments API schema has no `gatewayRefusalCode`, so a Payments API `refusalCode` cannot be classified as raw or Worldpay from the payload alone.

### 5.4 Lifecycle by operation (card)

- **Authorization**: `outcome: authorized` (201) / `refused` (201); webhook `sentForAuthorization` -> `authorized` or `refused` or `error`. 3DS adds `3dsDeviceDataRequired` -> `3dsChallenged` -> final outcome. Partial authorization: `amounts.totalAuthorized` below `amounts.requested`.
- **Capture/settlement**: settle action -> HTTP 202 `sentForSettlement`; webhook `sentForSettlement`, optionally `settled` or `settlementFailed`. Auto settlement: the authorization response itself is `sentForSettlement`.
- **Cancel (void)**: 202 `sentForCancellation`; webhook `cancelled`. With auto settlement, AVS/CVC `notMatched` leads to automatic `sentForCancellation` unless disabled.
- **Expiry**: webhook `expired`.
- **Refund**: 202 `sentForRefund` / `sentForPartialRefund`; webhook `sentForRefund` (online refunds carry an authorization code), optionally `refunded`, or `refundFailed` with `refund.refusal`.
- **Reversal**: Payments API `sentForReversal`; Card Payments v7 reversal "is processed as a cancel or refund request" depending on elapsed time (US entities refunded one day after, others after 15 minutes). The webhook for a reversal is therefore `cancelled` or a refund event; a dedicated reversal webhook is NOT DOCUMENTED.
- **Chargeback**: card chargeback lifecycle in Access webhooks is limited to `informationRequested`; `chargedBack` is Klarna-only. APM `lastEvent` has dispute states. A separate Disputes API exists in the API directory (`/apis/disputes`); it was not read.
- **Payouts**: card payout events above; account payouts use a separate format.
- **Subscriptions/rebills**: recurring payments are merchant-initiated requests using customer agreement types `subscription`, `installment`, `unscheduled`. Subscription objects or subscription states are NOT DOCUMENTED on the pages read.

## 6. Notifications / webhooks

### 6.1 Access Events delivery

- **Transport**: HTTPS POST to a URL boarded by the Implementation Manager (Enterprise) or set in the dashboard (SMB). The URL needs a certificate from a trusted CA with SHA-256 or better across the chain.
- **Body**: JSON, `application/vnd.worldpay.events-v1.hal+json`.
- **Source IPs**: 33 addresses listed on the events page, port 443.
- **Acknowledgement**: HTTP `200`. "Not acknowledging can cause delays (or loss) of subsequent events in the queue."
- **Retries**: if no `200` within 10 seconds, the event is retried with growing intervals until acknowledged, for up to one week. Interval wording differs: "starting 30 seconds to 2 hours" (events page) vs "starting 15 minutes to 2 hours" (HPP webhooks page).
- **Ordering**: NOT DOCUMENTED. The queue wording suggests per-merchant sequencing, but no guarantee is stated.
- **Duplicates**: retries make duplicates possible. Whether a retried delivery keeps the same `eventId` is NOT DOCUMENTED.
- **Opt-in events**: `settled`, `settlementFailed`, `refunded` and `informationRequested` are "only available in certain use cases". Event availability also differs by business type (overview table).

| `eventDetails.amount.value`, `.currencyCode`                             | Amount as an integer "with an exponent of 2"                                                                                                                                                                                                                                |

The `refused` event has **no refusal code or description field**. The decline reason must come from the synchronous response or Payment Queries (`events[].code`).

`tokenCreated` adds `eventType`, `notificationId` (UUID) and `createdAt` (with `Z`) at top level, and in `eventDetails` carries `tokenCreatedAt`, `tokenPaymentInstrument` (`type`, `href`), `tokenExpiryDateTime`, `description`, `tokenId`, and a `paymentInstrument` with masked `cardNumber`, `cardHolderName`, `cardExpiryDate`, `bin`, `brand`, `fundingType`, `countryCode` and a full `billingAddress`.

### 6.3 Signature and authenticity (sensitive; do not verify)

- **`Event-Signature` header** (opt-in through the Implementation Manager): format `{keyId}/{hashFunction}/{signature}`, for example `1/SHA256/...`; several comma-separated signatures may be present in any order. HMAC over the raw body with a shared secret; only SHA256 is listed. Merchants should answer `400` if the signature is missing or wrong.
- **Mutual TLS** alternative: client certificate subject contains `Payment Status Event Sender` (`Payment Status Event Sender (secure-test)` on Try), root CN `UKDC1-PC-PKI02`.
- PandaPayLens should redact `Event-Signature` values when headers are pasted and never ask for the shared secret. It may report "signature header present, key ids N" as metadata.

### 6.5 Other notification channels

- **WPG order notifications**: XML (`text/xml; charset=UTF-8`) over HTTPS, or email; CGI/Text on request. Acknowledge with HTTP 200 and body `[OK]` within 30 seconds; retries from 30 seconds to 2 hours, removed after 7 days. `AUTHORISED` and `REFUSED` are sent immediately; other statuses "typically within 15 minutes". Authenticity by client certificate (`Payment Status Event Sender`, root `WPG Client Root CA`) or reverse DNS `*.worldpay.com`. No signature field.
- **Account payouts webhooks**: JSON `PaymentOutNotification` with `originalPaymentInfo` and `paymentResult`; merchant answers `PaymentOutNotificationResult` `SUCCESS` or `ERROR`; HMAC verification "highly recommend[ed]". Out of scope.

## 8. Sensitive fields

Redact or mask by default. Request fields are included because developers often paste request/response pairs.

- **Card data**: `paymentInstrument.cardNumber` (full PAN in requests), `cvc`, `cardHolderName`, `expiryDate`/`cardExpiryDate`, `tokenNumber` (DPAN), `cardBin` + `lastFour` together, masked `cardNumber` in `tokenCreated`, `paymentAccountReference`, `fpanLastFour`.
- **Authentication data**: `authentication.networkToken.cryptogram`, 3DS `authenticationValue`/CAVV (v6 `customer.authentication.authenticationValue`), `eci`, 3DS `transactionId`, `challenge.jwt`, `challenge.payload`, `challenge.url`.
- **Personal data**: `billingAddress` (in `tokenCreated` and requests), `shippingAddress`, `email`, `phone`, customer names, `recipient` (financial services data), `fundsTransfer` sender/recipient data.
- **Secrets and credentials**: `Authorization` header (Basic Auth), `Event-Signature` header, Checkout SDK `sessionHref`, token `href`s, `_links`/`_actions` link data (encrypted per-payment capability links; treat as sensitive), account payout HMAC values.
- **Merchant identifiers**: `merchant.entity`, WPG `merchantCode`, `notification` URLs.
- **Account payouts**: `iban`, `accountNumber`, `walletIdentifier`, `payee`.

## 9. Structural detection hints

Strong Worldpay signals (combine several):

1. **Events webhook**: top-level keys `eventId` (UUID), `eventTimestamp`, `eventDetails`; `eventDetails.classification` in {`payment`, `payout`, `chargeback`} and `eventDetails.type` from section 5.2; usually `eventDetails._links.payment.href` equal to `""`. `tokenCreated` adds `eventType`, `notificationId`, `createdAt`. Media type `application/vnd.worldpay.events-v1.hal+json`; header `Event-Signature: <n>/SHA256/<hex>`.
2. **Payment response**: `outcome` with a Worldpay value (`authorized`, `refused`, `sentForSettlement`, `Sent for Settlement`, `3dsDeviceDataRequired`, `fraudHighRisk`, ...) together with `paymentId` and `commandId`; `refusalCode` as a numeric string with `refusalDescription`; `advice.code`; `riskFactors[]` objects with `type`/`risk`/`detail`; `paymentInstrument.type` such as `card/plain+masked`, `card/network+masked`, `card/tokenized`.
3. **Links**: `_links` keys namespaced `cardPayments:*` or `payments:*` with `curies` pointing at `https://try.access.worldpay.com/rels/...`; `_actions` keys `settlePayment`, `cancelPayment`, `reversePayment`, `partiallySettlePayment`; hosts `try.access.worldpay.com`, `access.worldpay.com`.
4. **Error**: `errorName` + `message`, optional `validationErrors[]` with `jsonPath` starting `$.`, or `headerName`. The camelCase `errorName` key is distinctive.
5. **Payment Queries**: `lastEvent` in the `authorizationSucceeded` style plus `events[]` with `eventName`, `timestamp`, `commandId`.
6. **XML (report as unsupported)**: WPG root `<paymentService version="1.x" merchantCode="...">` with `<reply>`, `<notify><orderStatusEvent orderCode="...">`, `<lastEvent>`, `<ISO8583ReturnCode code= description=>`, `<error code="1-14">`; cnpAPI namespace `http://www.vantivcnp.com/schema`, root `cnpOnlineResponse` with `response`, `message`, `version` attributes, `cnpTxnId`.

Differences from supported and candidate providers:

- **Stripe**: JSON objects carry `object` and prefixed `id` (`pi_`, `ch_`, `evt_`); events use dotted `type`. Worldpay has no `object` field and uses `outcome`/`eventDetails.type`.
- **Adyen**: `pspReference`, `resultCode` (`Authorised`, `Refused`), `refusalReason`/`refusalReasonCode`, notifications `notificationItems`/`NotificationRequestItem`/`eventCode`. Worldpay uses `refusalCode`/`refusalDescription` and `outcome`; the shared word "refusal" is not enough, check for `paymentId`+`commandId` or `pspReference`.
- **payabl.**: URL-encoded `key=value` strings; Worldpay Access is JSON.
- **Checkout.com**: `action_id`, 5-digit `response_code` (`10000`), `approved` boolean, `_links`; events `id`/`type`/`data`. Both use `_links`; Worldpay keys are `cardPayments:*` with `curies`, Checkout uses plain keys.
- **PayPal**: `event_type` (`PAYMENT.CAPTURE.COMPLETED`), `resource`, `resource_type`.
- **Braintree**: webhooks are form-encoded `bt_signature` + `bt_payload`.
- **Mollie**: `resource: "payment"` or `resource: "event"`.
- **Square**: `merchant_id`, `event_id`, dotted `type` (`payment.created`).
- **NMI**: URL-encoded `response`, `responsetext`, `authcode`, `response_code`.
- **MiFinity** (supported adapter): also uses `transactionReference`; never treat `transactionReference` alone as a Worldpay signal.
- **Finrax** (supported adapter): uses `paymentId`; require `commandId`, `outcome` or the `eventDetails` envelope as well.

## 10. Limitations, ambiguities and documentation inconsistencies

1. **Footnote markers merged into codes**: the refusal table shows `131` and `652`; these are codes `13` and `65` with footnotes 1 and 2. An adapter must not add 131 or 652 as codes.
2. **Raw vs Worldpay codes in one field**: `refusalCode` carries either the Worldpay code or the raw scheme/acquirer code depending on merchant configuration. Only Card Payments v7 adds `gatewayRefusalCode`. Overlaps: Amex raw `106` (PIN attempts exceeded) vs Worldpay `106` (invalid account); raw `05` vs Worldpay `5`; raw `51` is insufficient funds for Visa/Mastercard but a generic decline for Discover. Without `gatewayRefusalCode` the adapter should report both readings or prefer the Worldpay table and mark it uncertain.
3. **`refused` webhook has no reason**: decline codes are only in synchronous responses, Payment Queries events, and `refundFailed` (`refund.refusal`).
4. **Status vocabularies differ** across APIs: `sentForSettlement` (Payments API, events), `Sent for Settlement` (Card Payments v7 outcome and `lastEvent`), `settlementRequested`/`settlementRequestSubmitted` (Payment Queries), `CAPTURED` (WPG). Card Payments v7 `lastEvent` is Title Case and one enum misspells `Send for Cancellation`. The APM manage page lists `disputInformationSupplied` while the OpenAPI has `disputeInformationSupplied`.
5. **Testing pages use v6 names** (`code`, `description`, `rawCode`, `refusalAdvice`) while v7 and the Payments API use `refusalCode`, `refusalDescription`, `advice.code`. Pasted v6 payloads may still use the old names.
6. **Test magic values disagree with the reference table** (section 4.1): `17`, `29`, `38` appear only in tests; `8`, `28`, `63`, `75` have different texts.
7. **Same code, different text**: code `5` is "REFUSED" (responses), "Do not honour" (Payment Queries example) and "Do not honor" (refund refusal example).
8. **Retry interval wording** differs between the events page (30 seconds to 2 hours) and the HPP webhooks page (15 minutes to 2 hours). The events page also mentions possible "loss" of subsequent events while stating a one-week retry.
9. **Events overview vs OpenAPI**: `settlementInstructed`, `settlementRejected`, `topUpAccepted`, `topUpRejected` and `requestExpired` are in the OpenAPI but not in the overview table. Payout `refused` and payment `refused` share the same `type` string; only `classification` separates them.
10. **`riskFactors` enums differ**: Card Payments v7 schema allows `type` `riskProfile` and `risk` `verificationFailed`; the Events schema allows `nameInquiry`, `partialMatched`, `notSupported` and name `detail` values.
11. **Amount exponent**: events describe `amount.value` as "a whole number with an exponent of 2", but the WPG currency table lists exponent 0 (for example XOF, VND) and 3 (BHD), and the v7 migration changed CLP, CVE, ISK, UGX from 0 to 2. Whether every Access currency uses exponent 2 is unclear; the adapter should not hard-code a divisor for all currencies without a table.
12. **Timestamps**: `eventTimestamp` examples have no time zone; `eventDetails.date` is the original submission date, not the event date. Payment Queries timestamps are ISO 8601 with `Z`.
13. **Error naming**: the error page names the 500 error `internalErrorOccurred`; the Card Payments v7 OpenAPI uses `internalServerError`. Authentication failure is `accessDenied` (401, or 403 in Tokens) but `unauthorized` in APMs. The APM OpenAPI uses the field name `transactionReference` as an `errorName` in two Swish examples with the same message.
14. **OpenAPI defects**: the Card Payments v7 400 response media type is written `aapplication/vnd.worldpay.payments-v7+json`.
15. **Opt-in and use-case-dependent events**: `settled`, `settlementFailed`, `refunded`, `informationRequested`; raw codes; `Event-Signature`. Payload content depends on merchant set-up.
16. **WPG docs**: the troubleshoot page lists error codes 1-8 while the DTD defines 1-14; the payment process page contains an unedited note ("Needs to include Refund_Failed as an outcome for refused online auth refunds"). WPG and cnpAPI pages are client-rendered; their `index.md` text flattens tables and drops XML examples.
17. **Account payouts**: the `paymentState` field "does not currently reflect the actual status of a payout" until "H2 2026".
18. **Card chargebacks**: beyond `informationRequested`, card dispute states are NOT DOCUMENTED for Access webhooks.
19. **Query delay**: Card Payments events query can lag up to 15 minutes; APM queries "may take additional time".
20. **cnpAPI SDKs are archived** on GitHub (cnp-sdk-for-java, -dotnet, -php, -ruby and the chargeback SDKs); the XSD in the Java SDK is v12.49.
