# Checkout.com provider research (adapter id: `checkout`)

> Research notes for a parse-only PandaPayLens adapter. Every fact below was taken from Checkout.com's official documentation (www.checkout.com/docs) or its official OpenAPI spec (api-reference.checkout.com). Anything the docs don't cover is marked **NOT DOCUMENTED**. Category and retry-class columns are **PandaPayLens suggestions**, not Checkout.com classifications. Where Checkout.com publishes its own classification (soft/hard decline, Smart Dunning eligibility, downtime-retry eligibility), it is shown in separate columns.
>
> Verification date: **2026-10-25**. The API response codes page showed "Last updated: October 21, 2026" when it was read.

## 2. API families and versions in scope

- **Unified Payments API** (`POST /payments`, `GET /payments/{id}`, `GET /payments/{id}/actions`, `POST /payments/{id}/captures|refunds|voids|reversals|authorizations|cancellations`). Base URLs are `https://{prefix}.api.checkout.com` and `https://{prefix}.api.sandbox.checkout.com` (S11). This is the only payments API the current docs and spec describe.
- **Workflows / webhooks** (`/workflows`, `/workflows/events/{eventId}`, `/workflows/events/subject/{subjectId}`). This is the current webhook delivery model (S14, S22).
- **ABC vs NAS.** The current official docs and API reference never use the terms "ABC" or "NAS". The legacy "previous" docs and API reference return 404 (S23). The account-model differences therefore can't be confirmed from official docs as of 2026-10-25: **NOT DOCUMENTED (legacy docs removed)**. The current docs describe what was formerly called the NAS platform. Signs of that: per-merchant `{prefix}` subdomains, `processing_channel_id`, entities (`ent_`), and Workflows-based webhooks.
- **Target first:** the Unified Payments API (current/NAS) payment responses and errors, plus Workflows webhooks for the `gateway` event types (payment__, card_verification__). Disputes (`dispute_*`) can come in a second phase. Issuing, Identities, Platforms and Payment Setup events are out of scope initially.
- **Event payload versioning.** Each webhook carries a `version` string. The examples show `1.0.29` for most gateway events, `1.0.9` for pending/canceled/expired/capture_pending/refund_pending, `1.0.34` for retry_scheduled, `1.0.43` for payment_paid, and `1.0.3` for compliance_review (S18). Responses carry a `Cko-Version` header (S22). Version compatibility rules: **NOT DOCUMENTED**.

## 3. Error response format and payment response shape

### 3.1 Error responses (4xx)

The docs say: a 2xx response contains `response_code` (and `response_summary`, `status`), and a 4xx response "may contain an `error_codes` field" (S1).

OpenAPI `ValidationError` (S22), used for 422 on `/payments`:

```json
{ "request_id": "string", "error_type": "string", "error_codes": ["string"] }
```

The OpenAPI `Error` schema (S22) has only `request_id` and `error_type` (example `request_malformed`).

**Example 1: 422 Invalid data was sent** (verbatim from S4 and S8):

```json
{
  "request_id": "0HL80RJLS76I7",
  "error_type": "request_invalid",
  "error_codes": ["payment_source_required"]
}
```

**Example 2: 422 refund authorization declined** (verbatim from S8, https://www.checkout.com/docs/payments/manage-payments/refund-a-payment/refund-a-payment-with-a-reference.md):

```json
{
  "request_id": "f5feff3f-d2ef-4c82-b4d0-ff443731581f",
  "error_type": "processing_error",
  "error_codes": ["refund_authorization_declined"]
}
```

`error_type` values seen in official sources:

| Value                                                                                  | Where it appears                                                            |
| -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `request_invalid`                                                                      | 422 examples (S4, S8), and the 429 schema example on `POST /payments` (S22) |
| `processing_error`                                                                     | Refund authorization declined, 422 (S8)                                     |
| `request_malformed`                                                                    | `Error` schema example (S22)                                                |
| `base_url_invalid`                                                                     | 403 when the merchant-specific subdomain is not used (S11)                  |
| `conflict`, `not_found`, `unprocessable_entity`, `validation_error`, `invalid_request` | Appear in other API areas of the spec (S22), not the payments examples      |

A complete `error_type` enum for payments is **NOT DOCUMENTED**.

`request_id` formats vary: a short id (`0HL80RJLS76I7`) and a UUID both appear. Treat it as an opaque string. The request id is also returned in the `Cko-Request-Id` response header (S22).

**HTTP statuses** documented for `POST /payments` (S22): `201` Payment processed successfully, `202` Payment asynchronous or further action required, `401` Unauthorized (no body schema documented), `422` Invalid data was sent, `429` "Too many requests or duplicate request detected" (body example `error_codes: ["duplicate_request"]`), `502` Bad gateway.

For captures, refunds and voids (S22):

| Status | Meaning                          |
| ------ | -------------------------------- |
| `202`  | Accepted                         |
| `200`  | Already captured/refunded/voided |
| `403`  | Capture/Refund/Void not allowed  |
| `404`  | Payment not found                |
| `422`  | Invalid data                     |
| `502`  | Bad gateway                      |
| `429`  | Too many requests (refunds only) |

The general HTTP list on S1 is 200, 201, 202, 204, 400, 401, 403, 404, 406, 409, 412, 422, 429, 500, 502, 503, 504. S1 labels 204 "Non-Authoritative Information", which is a docs inconsistency. Idempotency conflict: `409 Conflict with another request being processed` (S10).

### 3.2 Payment response shape

`PaymentResponse` properties (S22, `POST /payments` 201): `id`, `action_id`, `amount`, `amount_requested`, `currency`, `approved`, `status`, `auth_code`, `response_code`, `response_summary`, `expires_on`, `3ds`, `risk`, `source`, `customer`, `balances`, `processed_on`, `reference`, `subscription`, `processing`, `eci`, `scheme_id`, `retry`, `_links`.

**Example: decline with raw scheme code** (verbatim from S1, "Response example"):

```json
{
  "response_code": "20051",
  "response_summary": "Insufficient funds",
  "processing": {
    "scheme": "visa",
    "partner_response_code": "51"
  }
}
```

**202 Pending** (S4): `{ "id", "status": "Pending", "reference", "customer", "3ds", "instruction", "_links": { "self", "redirect" } }`. There is no `response_code` in this example.

**Interpreting a request response** (S4): a 201 with `"approved": true` and `"status": "Authorized"` means the authorization succeeded. A 202 means a redirect or other further action is required, for example for 3DS. A **declined payment comes back as HTTP 201 with `approved: false`, `status: "Declined"` and a 2xxxx/3xxxx/4xxxx `response_code`**, not as an HTTP 4xx. The `Declined` enum value supports this; a verbatim 201-declined example in the docs is **NOT DOCUMENTED**.

**Capture/refund/void accepted** (S8, S22): `{ "action_id": "act_...", "reference": "...", "_links": { "payment": { "href": ".../payments/pay_..." } } }`. Refunds are asynchronous; the 202 does not confirm success (S8).

## 4. Codes

Documented decline classification (S1):

| Range | Documented type            | Meaning per S1                                                                                                                                                  |
| ----- | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 10xxx | Approved                   | The payment request was successful                                                                                                                              |
| 20xxx | Soft declines              | Declined, "though subsequent attempts may succeed"                                                                                                              |
| 30xxx | Hard declines              | Declined; "Most hard declines require the issuer or cardholder to fix any outstanding issues before you can retry"                                              |
| 4xxxx | Risk responses             | `response_code` and `status` depend on your Fraud Detection risk strategy actions. Sub-ranges: 41xxx client-level, 42xxx entity-level, 43xxx Checkout.com-level |
| 50xxx | Payout and Refund declines | Checkout.com declined the payout or refund                                                                                                                      |

Response codes are strings, and some contain letters (`2005C`, `2006P`, `200A4`, `200P1`, `200R1`, etc.). The spec examples for actions show `response_code` as a number (`10000`), even though the schema type is `string` (S22). The parser must accept both.

Checkout.com's own retry signals:

| Signal                               | Source                                           | Details                                                                                                                                                                 |
| ------------------------------------ | ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Smart Dunning eligible soft declines | S19                                              | `20005, 20013, 20014, 20015, 20016, 20020, 20022, 20030, 20051, 20057, 20061, 20065, 20068, 20078, 20096, 20098, 200P1, 20104, 20105`                                   |
| Automatic downtime retry eligible    | S19                                              | `20068, 20091, 20096`                                                                                                                                                   |
| Retry with 3DS                       | S1, S20                                          | `43401` ("Retry the transaction with 3D Secure"); `20154` is an SCA soft decline                                                                                        |
| Recommendation codes                 | S3, in `processing.recommendation_code`          | `01` updated/additional info required, `02` try again later, `03` do not try again                                                                                      |
| Mastercard MAC                       | S3, in `processing.partner_merchant_advice_code` | `01`-`04`, `21`, `24`-`30` (retry after 1h…10 days), `40`, `41`, `42`. The MAC/recommendation code should **override** the generic range-based retry class when present |

### 4(a) API validation `error_codes` (S2)

Field validation pattern (S2): `<OBJECT_NAME>_<VALIDATION_ERROR_TYPE>`, for example `destination_account_holder_first_name_too_long`. The validation error types are:

| Suffix           | Meaning per S2                                  |
| ---------------- | ----------------------------------------------- |
| `too_short`      | The value has too few characters                |
| `too_long`       | The value has too many characters               |
| `required`       | The field is required but no value was provided |
| `invalid_option` | The field is not a valid option                 |
| `invalid_format` | The value is not in the correct format          |
| `invalid`        | The field or value is invalid for other reasons |

Map any unknown code with these suffixes to `invalid_request` / `do_not_retry`.

Two families are templated:

- `{CURRENCY}_currency_not_configured`, for example `usd_currency_not_configured`
- `{SCHEME}_scheme_not_configured`, for example `visa_scheme_not_configured`

Additional codes seen elsewhere in official docs:

| Code                            | Source           | Suggested category         | Suggested retry |
| ------------------------------- | ---------------- | -------------------------- | --------------- |
| `duplicate_request`             | S22, 429 example | duplicate_request          | do_not_retry    |
| `refund_authorization_declined` | S8               | card_declined              | manual_review   |
| `payment_source_required`       | S4               | Already in the table below |                 |

## 6. Webhooks

### 6.1 Envelope

The workflow event schema (S22, `GET /workflows/events/{eventId}`) is: `id` (event id, example `evt_...`), `source` (example `gateway`), `type`, `timestamp` (date-time), `version`, `data`, `action_invocations[]` (`workflow_id` `wf_...`, `workflow_action_id` `wfa_...`, `status`, `_links.self`), and `_links`.

The per-event examples (S18) use **two envelope variants**:

| Variant                                          | Fields                                                                                                                                                                 | Events (examples)                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

| C, Payment Setup API                             | flat: `id: "set_..."`, `event_type`, `event_version`, `event_timestamp`, `event_subject_id`, `event_data` (base64), `correlation_id`, `idempotency_key`, `event_links` | payment_method_ready                                                                                                                                                                                                                                                                                                                                                                                                     |

### 6.3 Duplicates, ordering, retries, signature

- **Delivery** (S13, S14): "Checkout.com guarantees to send webhooks at least once, but the order in which we send them may vary." Don't rely on order.
- **Duplicate identification:** the event `id` (`evt_...`) is the natural dedupe key. S15 warns that "Resending a webhook manually may cause duplicates if any automatic retries are scheduled". The docs don't state explicitly that a resent or retried delivery keeps the same `evt_` id, so that is **NOT DOCUMENTED**. The id is presumed stable, because resend targets an existing event by `evt_` id.
- **Payment Setup events** carry an explicit `idempotency_key` (S18 payment_method_ready).
- **Ordering for a timeline:** sort by `data.processed_on`, then by `created_on`/`timestamp`, and fall back to the order the payloads were pasted. No sequence number is documented.
- **Automatic retries** (S13): up to 8 resends at 5m, 10m, 15m, 30m, 1h, 4h, 12h and 12h. The server must acknowledge within 10s (S14). Manual resend is limited to the last 90 days (S15).
- **Signature** (S13, S14): the `Cko-Signature` HTTP header holds a hex-encoded (Base16) HMAC SHA-256 of the **raw** request body, keyed with the workflow's signature key. Optionally, the merchant-defined key is sent in the `Authorization` header. Both are **sensitive**. PandaPayLens receives pasted bodies only, so it can't verify signatures. If either header is pasted, redact it.

Each authorization, capture, refund, void, etc. is an action on the payment. The authorization `action_id` can equal the payment id suffix (S4 example) |
| Event id            | `evt_` followed by 26 lowercase alphanumeric characters in the examples                                                                                                               | No pattern in the spec. One S15 example contains digits and a 0 (`evt_lzmo6p0i3612judj754w1ngtil`), so don't validate strictly                               |
| Workflow ids        | `wf_...` (pattern `^wf_[a-z0-9]{26}$`) and `wfa_...`                                                                                                                                  | S22                                                                                                                                                          |
| Other prefixes seen | `src_` source, `cus_` customer, `tok_` token, `pc_` processing channel, `ent_` entity, `cli_` client, `ca_` currency account, `set_` payment setup, `sid_` session (`cko-session-id`) | S4, S5, S11, S18                                                                                                                                             |
| `reference`         | Merchant-supplied order reference, for example `ORD-5023-4E89`                                                                                                                        | Present on the payment and on individual actions (captures and refunds can carry their own `reference`)                                                      |

**How captures, refunds and voids relate to the payment:** they do not get their own top-level ids. Each is an **action** (`act_...`) under the same payment `pay_...`. In webhooks, `data.id` is always the **payment id**, and `data.action_id` identifies the specific capture, refund or void. `_links.subject` points to `/workflows/events/subject/pay_...`, so the payment is the event subject. `GET /payments/{id}/actions` returns the full action history (S6, S22). A payment can have multiple partial captures or refunds, up to 150 partial actions in total (S8).

**Correlation key:** use `data.id` (pay_). Use `data.action_id` to tie a request response (202 `action_id`) to its webhook. Use `data.payment_id` for `payment_optimized`.

## 9. Structural detection hints

Strong positive signals for Checkout.com:

1. `data.id` matches `^pay_[a-z0-9]{26}$` and/or `data.action_id` matches `^act_[a-z0-9]{26}$`. Stripe uses `pi_`/`ch_`/`re_`, not `pay_`/`act_`.
2. `_links.self.href` / `_links.subject.href` contain `checkout.com/workflows/events/` (or `{prefix}.api[.sandbox].checkout.com`). `data.event_links` exists.
3. The envelope has `version` as a dotted semver-like string (`"1.0.29"`) **and** `created_on` (ISO-8601 with 7 fractional digits and `Z`) **or** `timestamp` plus `source` (`"gateway"`).
4. `response_code` is a 5-character string in the 10xxx-50xxx ranges, together with `response_summary`.
5. Payment responses have `approved` (boolean) plus a Title Case `status` from the enum in section 5, plus `balances.total_authorized` etc.
6. Error bodies have exactly `request_id` + `error_type` + `error_codes[]` (snake_case strings).
7. `type` is snake_case with a domain prefix: `payment_*`, `dispute_*`, `card_verified`, etc.

Notes on Stripe and Adyen, from general knowledge and **not verified in this research**:

- Stripe events also use `evt_`, `type` and `data`. Stripe has `object: "event"`, `api_version`, `livemode`, an integer `created` and `data.object`, none of which appear in Checkout.com payloads. Use the absence of `data.object` together with the presence of `pay_`/`act_` ids or `_links` as the discriminator. Don't rely on `evt_` alone.
- Adyen notifications use `notificationItems`/`NotificationRequestItem`, `pspReference` and `eventCode`, none of which appear in Checkout.com payloads.

Payment Setup events (variant C) are detected by `event_type` + `event_subject_id` + `id` starting with `set_`.

## 10. Limitations and ambiguities

1. **ABC vs NAS.** The legacy "previous" docs and API reference return 404 (S23). The shape of ABC-era payloads (old `/payments` responses, legacy webhooks) can't be verified. **NOT DOCUMENTED**. The adapter should target current Unified Payments API / Workflows shapes and label anything else "unknown shape".
2. **Envelope inconsistency.** Event examples mix `created_on` with `timestamp` + `source` (variants A and B), and the OpenAPI event schema uses `timestamp` + `source`. The parser must accept both.
3. **`links` vs `_links`.** The S4 201 example uses `links`; the schema and other examples use `_links`.
4. **Number vs string types.** `response_code`, `auth_code` and processing ids appear as numbers in some spec examples, but the schema says string.
5. **One code, several texts.** For example, `20109` has 3 response texts and `20019` has 2. `response_summary` text "may vary across different endpoint responses" (S1), and casing differs ("Declined - Do Not Honour" in webhooks vs "Declined - Do not honour" in the table). Key on `response_code`, never on `response_summary`.
6. **No complete `error_type` enum** for payments, and no complete `error_codes` list for captures, refunds and voids beyond the `/payments` table. **NOT DOCUMENTED**.
7. **Event id stability** across automatic retries and manual resends is **NOT DOCUMENTED**. Duplicates are explicitly possible (S15).
8. **No per-payment ordering guarantee** and no sequence number. Ordering is explicitly "may vary" (S13).
9. **Webhooks have no `status` field.** The payment status has to be inferred from the event `type` and `balances`.
10. **Invalid dates in docs examples** (`"2023-06-34..."`). Parse leniently.
11. **Response-code duplicates.** The 4xxxx descriptions for `42206` say "client-level" inside the entity-level table, which is a docs typo. The S1 HTTP list labels 204 "Non-Authoritative Information".
12. **Retry classes are suggestions.** The category and retry columns are PandaPayLens judgement calls based on documented text. Only soft/hard/risk range membership, Smart Dunning eligibility, downtime-retry eligibility, `43401`→3DS, and recommendation/MAC codes are Checkout.com-documented retry signals.
13. **`payment_returned` example** has no `version` and an older `created_on` style (2018). `payment_optimized` uses `data.payment_id`.
