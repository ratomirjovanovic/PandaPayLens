# CCBill (adapter id `ccbill`): high-risk provider research

Status: research notes for a parse-only PandaPayLens adapter. Nothing here is a guarantee about live behavior. Everything comes from CCBill's first-party documentation (`https://ccbill.com/doc/`), its official website and its official GitHub repository as published on the verification date. When a point is not documented, the text says **NOT DOCUMENTED**. Suggested categories and retry classes are suggestions, not CCBill statements.

- Verification date: **2026-10-25**
- Gate outcome: **`documentation_verified`** (see section B)
- Method: every page listed in section A was downloaded as HTML and read in full (tables extracted programmatically; every version tab of every webhook event was read). Page modification dates were taken from the site's own WordPress REST metadata (`https://ccbill.com/doc/wp-json/wp/v2/posts?slug=<slug>`). The RESTful API reference page renders OpenAPI files hosted on GitHub; the copies in the official `CCBill/restful-api-guide` repository were read in full. No login, signup or access request was made. No provider endpoint was called.

## E. Regional and regulatory limitations

- Visa/Mastercard processing: "you need to have business and legal presence within a designated region (U.S., Canada, or a Europe participating country)" with proof during application (list-of-countries page, which lists 44 countries/territories including the US, Canada, the UK, EU member states, Switzerland, Norway, Iceland, Liechtenstein and several microstates/territories).
- SCA: "it is only mandatory for cards issued by EU-based banks" (3DS FAQs). REST page: European merchants accepting European customers "need to implement an SCA solution"; non-European merchants accepting European customers are "highly recommended" to.
- Currencies: cards and CCBill Pay support "USD, EUR, GBP, AUD, CAD, JPY" (accepted-payment-methods). Webhook Appendix A lists exactly these six numeric codes (`036`, `124`, `392`, `826`, `840`, `978`).
- ACH: "Used in the U.S. and a small portion of Canadian customers"; "Transactions in USD only".
- High-risk card brand registration: CCBill collects "annual card brand fees for Mastercard ($1000) and Visa ($950)"; since 2021-04-17 MCC 7273 (US, Canada, EU, UK) and 5967 (EU, UK) are high-risk (risk-difference page).
- Acceptable Use Policy: gambling content prohibited; prohibited business list (see section D); 18 U.S.C. 2257 compliance required for applicable sites; on suspension "all rebilling members may be cancelled and all monies held for a period of six months to one year".
- CCBill Pay: "Supported only on English-language FlexForms".
- Licensing/regulator registrations: **NOT DOCUMENTED** in the pages read (not looked up in third-party registers, per the research method).

## 3. Response and error formats

### 3.1 Webhooks

- Transport: HTTP POST. Event identity is carried **only in the URL query string**: `clientAccnum` (6 digits), `clientSubacc` (4 digits), `eventType` (event name), `eventGroupType` ("At this time, only Subscription is a valid option").
- Body: URL-encoded `key=value&...` or a flat JSON object. In the JSON example all values are strings (`"clientAccnum":"999999"`).
- Documented headers in the raw example: `X-Allowed-Satellites: PHX,ASH,AMS`, `Content-Type`, `User-Agent: Java/1.6.0_03`, `Via: 1.1 wmq1.ccbill.com:3129 (squid/2.7.STABLE5), 1.0 internal`. The satellite location (Phoenix, Ashburn, Amsterdam) is chosen by the merchant.
- Timestamps: `timestamp` as `YYYY-MM-DD HH:MM:SS` (24h). Time zone **NOT DOCUMENTED**. Several doc examples write dates with a non-ASCII hyphen character (Unicode U+2010) instead of `-`; pasted examples may contain it, so a parser should normalize it.
- Dates: `nextRenewalDate`, `renewalDate`, `nextRetryDate` as `YYYY-MM-DD` (BillingDateChange example shows `2025-08-05 15:18:17`, so a time part can appear); ManualAdd `endDate` as `YYYYMMDD`, `00000000` meaning no end date.
- Amounts: decimal strings (`4.95`); currency as ISO 4217 numeric (`billedCurrencyCode`, `currencyCode`, `accountingCurrencyCode`) and, from Release 6, alpha (`billedCurrency`, `currency`, `accountingCurrency`).
- Pass-through values: any custom form variable is echoed back; "Always perpend Pass-through Key/Values with X-." (sic).
- Optional fields: "Some fields, such as avsResponse and cvv2Response, will not be sent if the associated features have not been configured by Merchant Support"; `paymentAccount` "must be configured by CCBill for data to be sent"; `lifeTimeSubscription` "Is not posted if not positive"; `flexId` only for FlexForms transactions.

### 3.2 Background Post (Approval / Denial Post URL)

Variables posted (Background Post page, "Postback" table): `accountingAmount`, `address1`, `affiliate`, `affiliate_id`, `affiliate_system` (`-1` unavailable, `1` CCBill, `2` WMS Affiliate, `3` Miscellaneous, `4` WMS Tracker), `allowedTypes`, `baseCurrency`, `cardType`, `ccbill_referer`, `city`, `clientAccnum`, `clientDrivenSettlement` (`1`/`0`), `clientSubacc`, `consumerUniqueId`, `country`, `currencyCode`, `customer_fname`, `customer_lname`, `denialId` (declines only), `email`, `formName`, `initialFormattedPrice`, `initialPeriod`, `initialPrice`, `ip_address`, `lifeTimeSubscription`, `password`, `paymentAccount`, `phone_number`, `price`, `productDesc`, `reasonForDecline`, `reasonForDeclineBeforeOverride`, `reasonForDeclineCode`, `reasonForDeclineCodeBeforeOverride`, `rebills` (`99` = indefinitely), `recurringFormattedPrice`, `recurringPeriod`, `recurringPrice`, `referer`, `referringUrl`, `reservationId`, `responseDigest`, `start_date`, `state`, `subscription_id` (approvals only), `typeId`, `username`, `zipcode`, plus custom variables passed into the form. ### 3.3 RESTful Transaction API

- Success content type `application/vnd.mcn.transaction-service.api.v.2+json` (or `v.1`). Error content type `application/vnd.com.cwie.error.v1+json`.
- HTTP status semantics: "2xx. A successful API request", "4xx. Failure due to request information", "5xx. Error due to an unexpected issue."
- **A declined charge is HTTP 200** with `approved: false`, `declineCode`, `declineText`, `denialId`.
- Charge response fields (`TransactionInfo`/`TransactionInfoV2`): `declineCode` (int64), `declineText`, `denialId` (integer), `approved` (boolean), `paymentUniqueId` ("Unique key connected to payment account"), `sessionId`, `subscriptionId` (v1 integer, v2 **string**), `newPaymentTokenId`.
- Payment token object: `paymentTokenId` (32 hex), `programParticipationId`, `originalPaymentTokenId`, `clientAccnum`, `clientSubacc`, `createdDatetime` (`YYYY-MM-DDTHH:MM:SS`, no zone), `timeToLive` (hours; `2147483647` = unlimited), `validNumberOfUse`, `subscriptionId`, `paymentInfoId`; widget responses add `errors`, `cvv2Response`, `avsResponse`.
- Error envelope: `id` (UUID, "used to locate an error in the logs"), `url` (relative request path), `errors[]` of `{field, message}`, `generalMessage`, `errorCode` (int32), `timestamp` (ISO 8601 with milliseconds and `Z`).
- `401` "does not have a response body" (OpenAPI); the error code page lists `401 | Unauthorized | N/A | invalid_token`.
- 3DS objects (`threedsInformation`, widget `authenticateCustomer`): `eci`, `protocolVersion`, `cardToken`, `scaIndicator`, `success`, `currency`, `amount`, `acsURL`, `authenticationValue`, `authenticationType`, `creq`, `dsTransId`, `acsTransId`, `challengeWindowURL`, `transStatusReason`, `transStatusReasonDetail`, `status` (example `Y`), `clientTransactionId`, `sdkTransId`.
- Widget errors use several shapes: `{"errors":[{message,field}],"generalMessage","timestamp"}` (no `errorCode`), the same wrapped in `{"error":{...}}`, an array of `{target, message, propertyName}`, and `{status, statusText, id, errorCode, generalMessage, url, timestamp, validationErrors, clientTransactionId}`.

### 3.4 Legacy CCBill API (CSV / XML)

- CSV: first line field names in double quotes, second line values (some examples are rendered on one line or as "Fields:/Values:" prose).
- XML: `<?xml version='1.0' standalone='yes'?>` with a `<results>` root; scalar results are `<results>1</results>`.
- `subscriptionManagement.cgi` returns `1` (success), `0` (failure) or a negative error code; `viewSubscriptionStatus` returns `cancelDate`, `signupDate` (`YYYYMMDDHHMMSS`), `chargebacksIssued`, `timesRebilled`, `expirationDate` (`YYYYMMDD`), `recurringSubscription`, `subscriptionStatus`, `refundsIssued`, `voidsIssued`.
- `billingApi.cgi` returns `approved` + `subscriptionId` (approved), `approved` + `denialId` + `declineCode` + `declineText` (denied) or `results` = negative code (error).

### 3.5 Data Link Extract

CSV, "All fields are returned inside quotation marks"; errors are text "preceded by an "Error:" string"; field set is merchant-configured. Timestamps are 14-digit `YYYYMMDDHHIISS`, except `YYYY-MM-DD` for REBILL and EXPIRE.

## 5. Lifecycle

Card, ACH/check, telephone and `DPEU` payments share one subscription model; CCBill is a subscription-first platform where even one-time purchases get a `subscriptionId` (REST "Single billing transaction" example with `initialPeriod: 0`). There is no separate authorize/capture state exposed in these formats (except merchant-driven settlement, below).

### 5.1 Subscription states

| State                                             | How it appears                                                                                                                                                                                |
| ------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Active, recurring, not cancelled                  | `subscriptionStatus=2`; webhook NewSaleSuccess/UpgradeSuccess/UpSaleSuccess/CrossSaleSuccess; RenewalSuccess on each rebill; Data Link `Subscription Status` `Y`                              |
| Active but cancelled (runs to end of paid period) | `subscriptionStatus=1`; webhook `Cancellation` ("future rebilling ... is canceled"), `source` `FORM`/`API`/`PHONE`, `reason`                                                                  |
| Inactive                                          | `subscriptionStatus=0`; webhook `Expiration` ("the user's access ends"); Data Link `EXPIRE` ("reached the end of their subscription period or been cancelled and reached their renewal date") |
| Reactivated                                       | webhook `UserReactivation` ("previously canceled subscription is reactivated"), with `nextRenewalDate`                                                                                        |
| Billing date moved                                | webhook `BillingDateChange` with new `nextRenewalDate`; legacy `extendSubscription` (`extendLength` days)                                                                                     |
| Manually granted access                           | webhook `ManualAdd` (`endDate`); legacy `manualAdd` / `manualRemove`                                                                                                                          |
| Lifetime                                          | `lifeTimeSubscription=1`, `lifeTimePrice`                                                                                                                                                     |
| Rebill counter                                    | `rebills` total (`99` = indefinitely); Data Link `Recurring Status` = remaining rebills                                                                                                       |

### 5.2 Initial payment

- Success: NewSaleSuccess webhook / Approval Post (`subscription_id`) / REST `approved: true` with `subscriptionId` / billing API `approved=1`.
- Decline: NewSaleFailure webhook (`failureCode`, `failureReason`, `transactionId`) / Denial Post (`reasonForDeclineCode`, `reasonForDecline`, `denialId`) / REST HTTP 200 `approved: false` / billing API `approved=0`.
- Soft decline with manual override (Web Verify): decline code `45`; if the consumer is approved by CCBill support within 24 hours the transaction becomes approved and the Background Post carries `reasonForDeclineCodeBeforeOverride`. "Merchants do not get notifications for these events" (the override itself), and "Rebill Declines and New Declines are not eligible" (web-verify page).
- Batched (pre-approved during outages): Data Link `Batched Transaction` `Y` = failed batch, `N` = successful batch.
- Merchant-driven settlement (CDS): pre-authorized, funds collected when the consumer first logs in; Background Post `clientDrivenSettlement`; Data Link type `CDS`.
- 3DS outcome: `threeDSecure` (NewSaleSuccess/Failure) and `scaResponseStatus` (upgrade/upsale/cross-sale events).

### 5.3 Rebill (recurring payment)

- Success: `RenewalSuccess` with `renewalDate`, `nextRenewalDate`, `billedAmount`/`billedCurrency`, accounting amounts.
- Failure: `RenewalFailure` with `failureCode`, `failureReason`, `renewalDate` and `nextRetryDate` ("The next time billing will be attempted"). The rebill retry schedule and the number of retries before expiry are **NOT DOCUMENTED**; the only signal is `nextRetryDate`. A RenewalFailure without a later RenewalSuccess is expected to end in `Expiration`, but that link is **NOT DOCUMENTED** explicitly.
- Data Link `REBILL` lists successful rebills only, with `Rebill Transaction ID`.

### 5.4 Upgrades, upsells, cross-sells

`UpgradeSuccess/Failure`, `UpSaleSuccess/Failure`, `CrossSaleSuccess/Failure` carry `originalSubscriptionId` (+ original account/subaccount) and `source`. Charging a REST payment token triggers an `UpSaleSuccess` webhook (RESTful Transaction API page). Legacy `chargeByPreviousTransactionId` creates a new subscription on `newClientAccnum`/`newClientSubacc` without cancelling the original.

### 5.5 Cancellation

`Cancellation` webhook; legacy `cancelSubscription` returns `1`; `viewSubscriptionStatus` shows `cancelDate` and `subscriptionStatus=1` until expiry. Note: legacy `refundTransaction` "will also cancel and expire the subscription, either for a partial or a full refund request" (Admin Portal refunds do not).

### 5.6 Refund, void, return, chargeback

| Event        | Meaning                                                                                                                                 | Source                                                                                   |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `Void`       | "voided before settlement"; legacy `voidTransaction` "The consumer will not be charged"                                                 | webhook, legacy API, Data Link `VOID`                                                    |
| `Refund`     | "fully processed transaction is refunded"; partial refunds allowed via `amount` ("cannot exceed the amount of the initial transaction") | webhook, legacy API (`refundTransaction`, `voidOrRefundTransaction`), Data Link `REFUND` |
| `Return`     | "funds are returned to the customer, for an ACH or EU Debit transaction" (Release 2: "check returns")                                   | webhook                                                                                  |
| `Chargeback` | "cardholder disputes a transaction and a chargeback is initiated"                                                                       | webhook, Data Link `CHARGEBACK`, `chargebacksIssued` counter                             |

Chargeback stages (retrieval, representment, reversal, arbitration) are **NOT DOCUMENTED**; only the initiation event exists. Whether a Refund/Chargeback/Void is followed by `Cancellation` or `Expiration` webhooks is **NOT DOCUMENTED**. `refundsIssued`, `voidsIssued`, `chargebacksIssued` counters in `viewSubscriptionStatus` give per-subscription totals.

### 5.7 Payouts and wallet transfers

Merchant payouts are mentioned only in Admin/accounting FAQs; no payout payload is documented (**NOT DOCUMENTED**). CCBill Pay stores consumer payment methods; no wallet transfer or balance states are documented. Keep these out of scope.

## 6. Notifications (Webhooks and Background Post)

### 6.1 Format and event types

- Webhooks: see 3.1. **20 event types**: `NewSaleSuccess`, `NewSaleFailure`, `UpgradeSuccess`, `UpgradeFailure`, `UpSaleSuccess`, `UpSaleFailure`, `CrossSaleSuccess`, `CrossSaleFailure`, `Cancellation`, `Expiration`, `BillingDateChange`, `CustomerDataUpdate`, `UserReactivation`, `RenewalSuccess`, `RenewalFailure`, `Chargeback`, `Return`, `Refund`, `Void`, `ManualAdd`. The docs title two of them "RenewalSuccess (Rebill)" and "RenewalFailure (Declined Rebill)"; the exact `eventType` string sent for these is presumably `RenewalSuccess` / `RenewalFailure` but no literal example shows it (**NOT DOCUMENTED** literally).
- `eventGroupType`: only `Subscription`.
- CustomerDataUpdate fires only when the consumer changes billing data at support.ccbill.com, not on Admin changes.
- ManualAdd fires on Admin Manual Add, the `manualAdd` API, or credentials re-added on the Subscription Information Page.
- Background Post: two post types (Approval Post URL, Denial Post URL) for payment form transactions; FlexForms cascades can use a "Post Proxy URL" for Background Posts.

### 6.2 Identifying the event when only the body is pasted

The body never contains `eventType`. Without the query string, a parser can only infer the event from the field set, and several events are **indistinguishable**:

- `Refund` and `Void` have identical field sets; `Chargeback` differs only by `bin`; `Return` lacks `cardType`, `currency`, `accountingCurrency`, `expDate`.
- `Expiration` (`subscriptionId`, `clientAccnum`, `clientSubacc`, `timestamp`) is a subset of every other subscription event.
- `failureCode` + `nextRetryDate` identifies RenewalFailure; `failureCode` with consumer fields identifies a *Failure sale event; `originalSubscriptionId` marks upgrade/upsale/cross-sale (which one cannot be told apart without `eventType`).
- `renewalDate` + `billedAmount` identifies RenewalSuccess.

Suggestion: report the inferred candidates and ask for the request line when ambiguous.

### 6.3 Versions

Each event configuration has a version (e.g. NewSaleSuccess v1-v8). "Whenever you create a new Webhooks configuration, it automatically uses the latest Webhooks version"; adding an event to an existing configuration upgrades only that event; changing the URL does not upgrade. The version is not sent; it can only be estimated from which fields are present (e.g. `cardSubType` implies the 2025-04-29 versions, `threeDSecure` NewSaleSuccess v6+, `flexId` v3+, `bin` v5+, `expDate`/`last4` v4+, `paymentAccount` v2+).

### 6.4 Signature and authenticity (sensitive)

- **No webhook signature or HMAC is documented.** Authenticity guidance is IP-based only: Webhooks from `64.38.212.1-254`, `64.38.215.1-254`, `64.38.240.1-254`, `64.38.241.1-254`; Background Post from the same four /24 ranges.
- `dynamicPricingValidationDigest` (webhooks) / `responseDigest` (Background Post): MD5 over `subscriptionId` + `1` (approved) or `0` (denied) + the merchant's salt (dynamic-pricing-user-guide). Present only with Dynamic Pricing, otherwise blank. Treat as sensitive; never attempt verification (needs the salt).
- `paymentAccount` is a 32-hex hash of consumer billing information, not a signature.

### 6.5 Delivery, retries, ordering, duplicates

- Webhooks: retry policy, expected acknowledgement (HTTP status or body), timeout and ordering are **NOT DOCUMENTED**. Up to four Webhooks URLs can be configured, so the same event may legitimately arrive at several endpoints.
- Background Post: "automatically resends unsuccessful posts up to 30 times over the course of a few hours"; what counts as unsuccessful is **NOT DOCUMENTED**.
- There is no event ID or delivery ID. Suggested dedupe key (suggestion): `eventType` + `subscriptionId` + `transactionId` (when present) + `timestamp`. For Background Post: `subscription_id` or `denialId`.

## 9. Structural detection hints

Strong CCBill markers (combine several):

- The pair `clientAccnum` (6 digits) + `clientSubacc` (4 digits) appears in every webhook body, Background Post, REST token object and legacy request. None of the supported providers (Stripe, Adyen, payabl., Checkout.com, PayPal, Braintree, Mollie, Square) or the other researched candidates use these names.
- Webhook request line `?clientAccnum=...&clientSubacc=...&eventType=<one of the 20 names>&eventGroupType=Subscription`; header `X-Allowed-Satellites: PHX,ASH,AMS`; `Via: ... wmq1.ccbill.com ...`.
- Webhook vocabulary: `subscriptionId` + `transactionId` + `timestamp` (`YYYY-MM-DD HH:MM:SS`), and families such as `billedInitialPrice`/`subscriptionInitialPrice`/`accountingInitialPrice`, `billedCurrencyCode`/`accountingCurrencyCode` (numeric ISO), `failureCode` + `failureReason` + `nextRetryDate`, `originalSubscriptionId`, `dynamicPricingValidationDigest`, `threeDSecure=AUTH_*`, `paymentType=CREDIT|CHECK|TELEPHONE|DPEU`.
- Background Post vocabulary: `reasonForDeclineCode`, `reasonForDecline`, `denialId`, `subscription_id`, `typeId`, `ccbill_referer`, `customer_fname`, `initialFormattedPrice`, `responseDigest`, `clientDrivenSettlement`.
- REST: media types `application/vnd.mcn.transaction-service.api.v.1+json` / `v.2+json` and `application/vnd.com.cwie.error.v1+json` (decisive when headers are pasted); charge body with `approved` + `denialId` + `declineCode` + `declineText` + `paymentUniqueId` + `newPaymentTokenId`; error envelope `id` (UUID) + `url` + `errors[{field,message}]` + `generalMessage` (often "Validation failed!") + 6-digit `errorCode` + ISO `timestamp`; token object with `timeToLive` + `validNumberOfUse` + `programParticipationId`.
- Legacy API: CSV with quoted header `"results"` or `"approved","subscriptionId"` / `"approved","denialId","declineCode","declineText"`, or `"cancelDate","signupDate","chargebacksIssued",...`; XML `<?xml version='1.0' standalone='yes'?><results>...`.
- Hosts and paths: `api.ccbill.com` (`/ccbill-auth/oauth/token`, `/payment-tokens/`, `/transactions/payment-tokens/`, `/wap-frontflex/flexforms/<uuid>`), `bill.ccbill.com/jpost/signup.cgi`, `bill.ccbill.com/jpost/billingApi.cgi`, `datalink.ccbill.com/utils/subscriptionManagement.cgi`, `datalink.ccbill.com/data/main.cgi`, `images.ccbill.com/flexforms/ccbill-widget-live.js`, `support.ccbill.com`.

Weak or shared fields (do not use alone): `transactionId` (also Finrax), `approved` (also eZeeWallet and Checkout.com docs), `timestamp`, `subscriptionId` (also Mollie), `email`, `amount`, `currency`. Versus other high-risk candidates: Verotel uses `saleID`/`shopID`/`event`/`signature`; NETbilling uses `status_code`/`trans_id`/`Ecom_Ezic_*`; neither uses `clientAccnum`. Versus payabl. (also URL-encoded): payabl. uses lowercase `transactionid`, `errormessage`, `status`/`errorcode`, never `clientAccnum` or `subscriptionId`.

## 10. Limitations, ambiguities and documentation inconsistencies

1. **Webhook event type lives only in the query string.** Body-only pastes cannot distinguish Refund from Void (identical fields), nor Upgrade from UpSale from CrossSale; Chargeback/Return are only weakly distinguishable (section 6.2).
2. **No webhook signature, event ID, retry policy, acknowledgement rule or ordering guarantee is documented.** Only IP ranges are given. Background Post retries "up to 30 times over the course of a few hours".
3. **Rebill decline codes are undocumented in practice**: `failureCode` is "Decline code sent from the bank" with the alphanumeric example `BE-140`, which matches no published table; Appendix B is numeric. The rebill retry schedule is not documented beyond `nextRetryDate`.
4. **Code `15` conflict**: the code tables say code 15 means "Your account is currently being processed...", but every billing API example shows `declineCode` `15` with `declineText` "declined by bank". Prefer the text when both are present.
5. **REST error numbers reused with different meanings**: `100105`-`100109` mean one thing at HTTP 400 (invalid payout type, privacy type, program category, payment type, program participation) and another at HTTP 500 (token creation failure, internal/Data Link error, IP range, deactivated account, failed logins). `200000` is both the REST validation error (400) and the 3DS "unknown issue" (500). `100100` is "Invalid client account" (400) in the table but also appears in a generic 500 example ("An error occurred, please try again later.").
6. Codes `130000`, `100015`, `100004` appear only in OpenAPI examples, not on the error codes page. The error codes page labels `200602` as "404 | Bad Request".
7. Error content type is `application/vnd.com.cwie.error.v1+json` in most specs but `application/vnd.com.cwie.error.v1.+json` (extra dot) in the GET charge spec.
8. Widget error objects have at least four different shapes (section 3.3), some without `errorCode`.
9. REST v1 `subscriptionId` and `denialId` are JSON numbers larger than 2^53 (precision loss in JavaScript); v2 makes `subscriptionId` a string but `denialId` remains an integer in both schemas.
10. Decline code `6` text is corrupted in both tables (a glossary sentence about date formats is spliced into "check your expiration date ... correctly").
11. Codes `22` and `34` have the same text; codes `11` and `46` have the same text; `23` and `56` nearly the same.
12. Field name casing differs: `flexId` (most events) vs `flexID` (UpSaleFailure, CrossSaleFailure tables); `lifeTimeSubscription` vs `lifetimeSubscription` (3DS billing API example). Parsers should match case-insensitively.
13. Copy artifacts in field tables: webhook `subscriptionId` described as "(Approval Post URL only)"; Return `amount` described as "The amount charged back"; Return/Refund currency descriptions mention "chargeback".
14. Content type typo: the guide says URL Encoded "uses the content type application/x-www-form-encoded" while the raw example header says `application/x-www-form-urlencoded`. The JSON example reuses `Content-Length: 102` from the URL-encoded one.
15. Dates in doc examples use a Unicode hyphen (U+2010) instead of ASCII `-` (e.g. the NewSaleSuccess `timestamp` example), so pasted doc samples may not parse as dates without normalization. The `-7` error article shows the `&curren` rendering defect (`sharedAuthentication=0` followed by a currency sign and `cyCode=840` instead of `&currencyCode=840`); a tolerant URL parser can repair it with a warning.
16. Webhook `timestamp` time zone is **NOT DOCUMENTED**; REST timestamps are UTC (`Z`); Data Link uses 14-digit stamps, or `YYYY-MM-DD` for REBILL/EXPIRE.
17. `dynamicPricingValidationDigest` for denied transactions is documented as MD5 of `subscriptionId` + `0` + salt, but failure events carry no `subscriptionId`.
18. Legacy API guide copy errors: the refundTransaction parameter table is headed `modifyUserCredentials`; the extendSubscription table is headed `manualRemove`; Example 1 says it views status but sends `action=cancelSubscription`; Example 2 describes subaccount `0002` but the request has none. The Data Link guide uses `merchantSubacc` in one example while the parameter is `clientSubacc`. The 3DS billing API table lists the action as `chargeByPreviousTransactionId` while the examples use `chargeByPreviousTransactionId3DS`.
19. Meanings of `scaResponseStatus` values `E, Y, N, A, U, R`, of `paymentType=DPEU`, of "Pre-Auth SC" (code 35) and "TGS" (code 52), and full `avsResponse`/`cvv2Response` value sets are **NOT DOCUMENTED**.
20. Whether `transactionId` on Refund/Void/Chargeback/Return is the original sale or the reversal record is **NOT DOCUMENTED**; whether a Cancellation/Expiration follows a refund or chargeback webhook is **NOT DOCUMENTED** (the legacy `refundTransaction` API says it cancels and expires the subscription).
21. The webhook version is not in the payload; versions must be guessed from fields (section 6.3).
22. Only one literal webhook body (Expiration) and no literal Background Post body is published; fixtures for other events must be synthesized from field tables and labelled as synthetic.
23. The REST resources page loads OpenAPI files from a non-CCBill GitHub account (`love-bees`) whose content differs slightly from the official `CCBill/restful-api-guide` repo; this research used the official repo.
24. The ISO Payment Gateway / ISO Merchant Account product has no public technical documentation on ccbill.com/doc; payloads from it are out of scope and its underlying platform is **NOT DOCUMENTED**.
25. Data Link CSV columns and order are merchant-configurable and the presence of a header row is **NOT DOCUMENTED**, so Data Link rows cannot be parsed reliably without the merchant's format.
