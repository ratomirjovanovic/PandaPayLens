# Segpay (adapter id `segpay`): high-risk provider research

Status: research notes for a parse-only PandaPayLens adapter. Nothing here is a guarantee about live behavior. Everything comes from Segpay's first-party documentation portal (gethelp.segpay.com) and its company website (segpay.com) as published on the verification date. When a point is not documented, the text says **NOT DOCUMENTED**. Suggested categories and retry classes are suggestions for PandaPayLens, not Segpay statements.

- Verification date: **2026-10-25**
- Gate outcome: **`documentation_verified`** (see section B), with the caveats in section 10.
- Method: every page listed in section A was downloaded as HTML and read as text. The documentation portal is a MadCap Flare site; its table of contents (`Data/Tocs/Master_Chunk0.js`, 145 pages) was used to find pages. Where Segpay publishes a postback example only as a screenshot, the screenshot image (an asset of the same first-party page) was viewed and transcribed; this is marked each time. No login, signup or access request was made. No Segpay API or postback endpoint was called. The SOAP WSDL files on srs.segpay.com were not fetched.
- Access note: the first automated request to https://segpay.com/ returned HTTP 403 from a bot filter; the same public page loaded normally with a standard browser `User-Agent` header. No credential was used anywhere.

Segpay runs **two technically separate products** that a developer may paste payloads from. This file keeps them apart:

- **Segpay Processing** (payment facilitator, hosted pay page `secure2.segpay.com/billing/poset.cgi`, Segpay-managed subscriptions, "postbacks"). Called "Processing" below.
- **Segpay Gateway** (merchant's own MIDs at third-party acquirers, XML API `gateway.segpay.com/cgi-bin/*.xcgi`, "Event Notifications"). Called "Gateway" below.

## E. Regional and regulatory limitations

- Merchant regions: US, EU (Ireland entity), UK (England entity), Australia ("Our newest market"; "AUD settlement", "AUSTRAC"). Home page states "75 Countries".
- Scheme programs: "registered as Visa and MasterCard Payment Facilitators in the EU, UK, and US" (Merchant Services page). RDR: "Presently, RDR is accessible exclusively to PSP accounts"; Payment Facilitator accounts "currently cannot enroll" (FAQ-RDR).
- PSD2/SCA: `SCArequired` applies to "Europe-to-Europe transactions in regions where PSD2 is enforced"; merchant-initiated rebills do not require SCA (PSD2 Transactions report).
- Visa/Mastercard reattempt rules apply to issuers "in Europe, AP, Canada and CEMEA" (Merchant Advice page).
- PayPal is unavailable in a documented list of 35 countries (PayPal Integration Guide).
- SEPA Direct Debit: 21 listed countries; mandates are region-bound (FAQ-SEPA, SEPA-GS).
- Pay by Bank: UK or supported EU bank account required; GBP/EUR only; no recurring (PayByBank.htm).
- Crypto: no recurring, no refunds (Crypto.htm).
- Merchants must meet KYC, AML and OFAC requirements (Merchant Services page); content rules in ComplianceDocs.

## 3. Response and error formats

### 3.1 Content types and encodings

- **Processing postbacks**: `key=value` pairs. Every published example is a full URL with a query string (for example `https://e2.toccata.com:82/PostbackApi/api/PostbackTest/Get?...`). The troubleshooting table says the merchant server must "Accept POST and GET". Which HTTP method is used, and the `Content-Type` of a POST body, are **NOT DOCUMENTED**. Default examples contain `method=Post` or `method=Get` as a parameter; its meaning is NOT DOCUMENTED.
- Values are URL-encoded (`transtime` is documented as "Sent URL-encoded"). Character set NOT DOCUMENTED. The docs say "Postbacks may include upper and lower-case characters. Do not require case-sensitive validation."
- **Merchant acknowledgement (Processing)**: configured "Expected Response" (e.g. `GOOD`, `OK`, `TransactionConfirmed`) and "Error Response" strings; no spaces, HTML or line breaks. Synchronous types (Inquiry, Enable, Disable) wait for the response and time out; transaction postbacks are asynchronous and use "standard HTTP response codes". Required response time: "Respond within 10-30 seconds" (Manage Postbacks).
- **Gateway XML API**: request XML posted in form variable `XMLData`; response `text/xml`, a `<data>` root with one element per request (`authresponse`, `creditresponse`, `cancelresponse`, `settlementresponse`, `rebillresponse`, `autopurchaseresponse`), all values as XML attributes. Some examples include an inline DTD.
- **Gateway Event Notification**: URL-encoded `key=value` string. Success = HTTP 200 "and any content in the body"; Segpay first performs a `HEAD` request and posts only if it gets a valid response. Content-Type NOT DOCUMENTED.
- **SRS**: reporting operations return .NET DataSet XML (`<DataSet xmlns="http://srs.segpay.com/MWS.asmx">` with `diffgr:diffgram` and `<Data diffgr:id="Data1" msdata:rowOrder="0">` rows); `ValidateUserAccess` returns `<int xmlns="http://srs.segpay.com/MWS.asmx">20213</int>`; admin operations return short strings (section 4.9); Reactivation returns a URL as plain text.
- **Membership Upgrade API**: JSON or XML by `Accept` header.

### 3.3 Member management postbacks

Documented triggers and "limited data" lists (06-Postbacks.htm):

- **Inquiry** (`action` default not stated on Processing page; MP page says `Probe`): when a username is collected; checks availability. Only when "Collect Username" is set. Required response `GOOD` (or configured). Full token list identical to Enable.
- **Enable**: after an approved purchase where a username is collected. Same data as Inquiry.
- **Disable** (default `Disable`): at expiry, or when expiration follows a chargeback or refund/cancel request. Data: action, username, purchase ID, transaction ID / refund reason code / refund code / refunded by ("available for refund/void/chargeback only"), custom variables.
- **Cancellation** (default `Cancel`): consumer cancels or requests refund and cancellation (MP: "requested either by you, Segpay or the consumer"). Data: action, username, purchase ID, transaction ID (for refund/void/chargeback), URL ID, cancellation reason code, cancellation code, cancelled by, custom variables.
- **Reactivation** (default `Reactivation`): cancelled or expired subscription reactivated. Data: action, username, purchase ID, URL ID, `billname`, `rval`, currency code, reactivation timestamp, `eticketid`, last bill date, next bill date, custom variables.

No full default example of any member management postback is published. Values of reason codes in Disable/Cancellation postbacks are NOT DOCUMENTED (see 4.9 for the only published reason code list, which belongs to SRS fraud blocking).

### 4.3 Processing `authcode` and other result strings

The format of `authcode` is not specified. Values shown in first-party examples:

- `00-Approved CVV:M` (SRS samples): issuer code, text, CVV result.
- `F460:Period1:Email:jane@email.com` (SRS declined sample): fraud code, rule period, attribute, attribute value (contains PII).
- `05:Do Not Honor: COF Expiration Date is Expired` (One-Click page, decline).
- `OK:0` (Membership Upgrade `transactionAuthCode` on approval).
- `SPXXXX: Transaction Cancelled by Consumer` with transaction ID `SPDECLINE` (crypto cancel; `SPXXXX` appears literally as a placeholder).
- `TestTrans` (SRS `AuthCode1` in a test sample).

Suggested parse: split on the first `:` or `-`; if the prefix matches 4.1 use that table; if it is a two-character issuer code use 4.7; otherwise keep as raw text.

## 5. Lifecycle

### 5.1 Processing subscription (card, PayPal, SEPA)

1. Signup: Inquiry (if username collected) -> transaction postback `trantype=Sale`, `action=Auth`, `stage=Initial`, `approved=Yes|No` -> Enable (approved, username collected). Trial if `iint`/`ival` set; `rval`/`rint` give the recurring terms.
2. Conversion: first rebill after the trial, `stage=Conversion`.
3. Rebill: later charges, `stage=Rebill`.
4. Instant Conversion: consumer converts early (`stage=Instantconversion`, `transguid` used as `ICToken`); only a transaction postback is sent ("Inquiry and Access postbacks will not be sent").
5. Failed rebill: transaction postback with `approved=No` and `stage=Conversion` or `Rebill`; the decline reason is in `authcode` (format see 4.3). Segpay retries failed rebills (Manage Consumers shows "retrying date" with "date(s) and reason(s) of the failed billing attempt(s)"; SRS has a `Retries` count; Scheduled Rebills report shows "anything in the retry process"). The retry schedule and the final outcome signal after retries are exhausted are **NOT DOCUMENTED** for Processing.
6. Cancellation: Cancellation postback; access continues to the next bill date (SRS CancelMembership). Expire: access removed immediately; Disable postback at expiry. Purchase statuses seen: "Recurring - Active", "Digital Purchase - Non Recurring", "Temporary Approval", Cancelled, Expired, SRS `PurchStatus` `Expired`, `NonRecurring`.
7. Reactivation: Reactivation postback (only for credit-card purchases on a price point with a Reactivation Offer, not cancelled for fraud).
8. Upgrade: Membership Upgrade API keeps the purchase ID; a transaction postback with `membershipupgrade=true` (example shows `stage=Conversion`).
9. Refund: transaction postback `trantype=Credit` with `relatedtranid`; options "Refund and Expire", "Refund and Cancel", "Refund Only" (Manage Consumers); Disable/Cancellation postbacks may follow. Void: `action=Void` (authorized but not captured). Refunds and voids are "briefly pending" in the portal; a pending postback state is NOT DOCUMENTED.
10. Chargeback: `trantype=Charge`; Disable postback when it ends access. Reversals: `CB Reversal` (chargeback won; does not reactivate the subscription), `RDRreversal` (Visa RDR auto-refund), `Revoke`.
11. Stand-In: bank unreachable -> temporary approval (Inquiry, Enable, Trans Post with `standin=1`); later bank decline -> void, a **new Trans Post with the same `tranid` and `purchaseid`**, and a Disable.
12. One-Click: recurring purchase gets a new purchase ID and is reported as Initial; one-time purchase reuses the purchase ID and is reported as a rebill.

Crypto (one-time only, no refunds): cancel -> `SPXXXX`/`SPDECLINE` postback; payment confirmed after 15 minutes enters a late window, after 30 minutes it is declined (declined postback). Pay by Bank: one-time only; postback markers NOT DOCUMENTED.

PayPal disputes: stage Inquiry -> Chargeback -> Pre-Arbitration -> Arbitration; channel separates internal disputes from external chargebacks and alerts.

Payouts: Segpay pays merchants weekly (Tuesday); no payout payload is documented. Wallet transfers: not applicable.

### 5.2 Gateway

`A` auth -> `S` settlement (Delayed Settlement products) or direct `S`/`I`; recurring: `I` then `R` rebills (Segpay-managed Dynamic Rebills or client-managed `rebillauth`), `K` conversion, `E` MaxRebill reached, `D` terminated, `M` cancelled (also auto-emitted after chargeback/fraud); `!` decline (decode `ResponseCode`); refunds `C`, `V`, `H` (pending batch), `F` (refund failed); disputes `1` retrieval, `U` alert, `Z` TC40, `X` chargeback; `@` pending bank-app confirmation; `T` test; `?` incomplete. `SubEventTypeID` adds trial/non-trial and the subscription state. "Flex Rebill" retry logic exists but its rules are NOT DOCUMENTED publicly.

## 6. Notifications / postbacks

### 6.1 Processing

- Types: Inquiry, Enable, Disable, Cancellation, Reactivation (synchronous); Transaction (asynchronous, up to 4 destinations, 2 reserved if Segpay Affiliate Master is used); PayPal Dispute (up to 2).
- Acknowledgement: configured "Expected Response" / "Error Response" strings; transaction postbacks use HTTP status.
- Retries (only if "Retry Postback" is enabled, which requires a failure email): member management every 5 minutes for up to an hour; transaction hourly for up to 12 hours.
- Ordering: **NOT DOCUMENTED**.
- Duplicate identification: no event or delivery ID is documented. `tranid` is unique per transaction ("For Voids, Credits, and Chargebacks, note that the tranID is unique"), but a Stand-In decline re-uses the temporary approval's `tranid` and `purchaseid`, and member management postbacks have no `tranid` in most cases. Suggested key: (`postback type`, `action`, `tranid` or `purchaseid`, `approved`, `trantype`). `postbackconfiguniqueid` identifies the configuration, not the delivery. Whether `processingtime` changes on a retry is NOT DOCUMENTED.
- Security: **no signature or HMAC field is documented.** Segpay publishes source IPs (`GetPostbackIPList` via SRS) and supports HTTP credentials for password-protected scripts (configured in the portal; not in the payload).
- Test mode: `TESTTRANS=1` (text) / `TESTRANS=1` (screenshot); "Rebills, refunds, and voids are currently not supported in TEST mode."

### 6.2 Gateway

- Events enabled by default: Auth, Single Sale, Initial Sale, Rebill, Cancellation, Termination, Credit, Chargeback, Decline. Enabled by emailing gateway support.
- "queued in the system when an event occurs and sent immediately in the order they are queued".
- HEAD probe first; up to 3 retries, then the post goes to a failover email address.
- Security: "The post can be done via SSL"; source IP list at `https://gateway.segpay.com/iplist.txt`. No signature documented.
- Duplicate identification: `TransactionID` per transaction plus `EventCode`; no event ID.

### 6.3 Signed artifacts (sensitive, PandaPayLens must not verify)

- MPI V4 result `signedJWT` (ES256, verifiable against `https://secure3d.segpay.com/.well-known/jwks.json`).
- Signed hosted pay page request `jwt` (HS256 with a merchant signing key; claims `iat`, `exp`, `jti`, `pageref`, `fields`).

## 9. Structural detection hints

Strong Processing markers (query/form string): `purchaseid` together with `eticketid` matching `^\d+:\d+$` (or `%3a`), `stage` in {Initial, Conversion, Rebill, Instantconversion}, `trantype` in {Sale, Credit, Charge, CB Reversal, CBReversal, RDRreversal, Revoke}, `approved=Yes|No`, `standin` in {-1, 0, 1}, `xsellnum`, `ival`/`iint`/`rval`/`rint`, `transguid`, `urlid`, `postbackconfiguniqueid`, and `transtime`/`processingtime` ending in `(GMT STANDARD TIME)`. Hosts in docs examples: `e2.toccata.com`, `e2.segpay.com`, `stagepostback.segpay.com` (Toccata, Inc. is Segpay's legal name). Pay page hosts: `secure2.segpay.com/billing/poset.cgi`, `pps2.segpay.com`, `pay.segpay.com`.

PayPal dispute postback: `disputeid=PP-R-...` plus `disputestage`, `disputechannel`, `currentstatus`, `action=Dispute*`, together with Segpay keys `purchaseid`, `urlid`, `transguid`. These Segpay keys distinguish it from a native PayPal payload.

Gateway Event Notification: `EventCode` with a one-character value from 4.4 (including `!`, `~`, `?`, `@`, `1`), `SubEventTypeID`, `SubscriberID`, `ProductCode` matching `^\d+-\d+-\d+$`, `OriginalEventCode`, `SitePassword`, `SiteUsername`, `Country` as 3 digits.

Gateway XML: root `<data>` containing `authresponse`/`creditresponse`/`cancelresponse`/`settlementresponse`/`rebillresponse`/`autopurchaseresponse` with `EventCode`, `ResponseCode`, `SubscriberID` attributes; DTD names `three65api` or `Segpayapi`.

SRS XML: namespace `http://srs.segpay.com/MWS.asmx`, `diffgr:diffgram`, `<Data diffgr:id="DataN">`, elements `eticketID`, `USERDATA` with `<EXTRA_DATA>`, `PurchStatus`, `AuthCode`.

Versus supported providers: payabl. also uses URL-encoded strings but with `transactionid`, `errorcode`, `orderid`, `security`; no overlap with `purchaseid`/`eticketid`/`stage`. None of Stripe, Adyen, Checkout.com, PayPal, Braintree, Mollie or Square use `purchaseid` + `eticketid`. Versus other high-risk candidates: their formats come from their own research files; this document makes no claims about them. Avoid detecting on generic keys alone (`price`, `currencycode`, `action`, `approved`, `email`, `username`, `desc`).

Custom postbacks are the main risk: the merchant chooses key names (`transid`, `transtype`, `subscriptionid`, `transaction`, `time` appear in Segpay's own examples). Detection should accept a payload as Segpay when enough value-shape markers match (eticket pattern, `(GMT STANDARD TIME)` timestamps, stage/trantype vocabulary), and mark field mapping as lower confidence.

## 10. Limitations, ambiguities and documentation inconsistencies

1. **Default postback key names are not tabulated.** The parameter table lists tokens; default keys are only visible in screenshots (Amount Verification, PayPal Integration, Stand-In FAQ). Keys seen there but absent from the table: `issingleusepromo`, `is3dsauthenticated`, `paymenttype`, `threedsversion`, `templatetype`, `paytype`, `paymentchoice`, `dynamicpricingid`, `dynamicdesc`, `dynamicdescriptor`, `merchantname`, `packagedescription`, `postbackconfiguniqueid`, `processingtime`, `uri`, `method`, `merchantid`. The device keys appear without the `extra` prefix.
2. **Custom postbacks use merchant-chosen key names**, so a pasted payload may use any keys.
3. No full default example of Inquiry, Enable, Disable, Cancellation or Reactivation postbacks; their values for reason codes are NOT DOCUMENTED.
4. `action` values differ across pages: the Processing guide gives defaults `Disable`, `Cancel`, `Reactivation`; the Merchant Portal page adds `Probe` (Inquiry), `Enable`, `Auth`, `Void`.
5. `trantype` spelling: `CB Reversal` (parameter table) vs `CBReversal` (matrix); `Revoke` only in the matrix; lowercase `sale`/`charge`/`credit` on the MP page. `stage`: `Instantconversion`, `INSTANTCONVERSION` (IC page), `Instant Conversion` (matrix). Case-insensitive matching is needed (Segpay itself warns about mixed case).
6. `cclast4` is described as "First 4 digits" in the parameter table and as last 4 on the MP page. `cancelledby`/`refundedby` are "Name of the consumer" vs "Admin name". The PayPal dispute table describes `billname` as an email address.
7. Test flag: `TESTTRANS=1` in text vs `TESTRANS=1` in the screenshot.
8. `currencycode` is documented as USD/EUR/GBP only, but AUD settlement, NOK (Amount Verification) and multi-currency are documented elsewhere.
9. `authcode` format is not specified (4.3). The documented fraud codes do not say which postback field carries them.
10. Timestamps: `M/D/YYYY h:mm:ss AM/PM (GMT STANDARD TIME)` in postbacks, `YYYY-MM-DD HH:MM:SS` in Gateway notifications, ISO 8601 with `+00:00` in SRS, `mm/dd/yyyy` for reactivation dates, `mmddyyyy` in SRS requests. Segpay says it "operates on GMT"; whether the label implies daylight saving is NOT DOCUMENTED.
11. Stand-In retries: "up to three times every two hours" (Processing guide, FAQ) vs "retried every 2 hours until an authorization response" (MPFeatures).
12. Processing rebill retry schedule, final failure signal and dunning emails are NOT DOCUMENTED. Gateway "Flex Rebill" retry rules are NOT DOCUMENTED.
13. Ordering of Processing postbacks and the HTTP method/Content-Type are NOT DOCUMENTED; the MP troubleshooting says to accept both GET and POST.
14. Acknowledgement: transaction postbacks "do not require a response" yet have an Expected Response field and are retried; MP troubleshooting says the response string is case-sensitive.
15. Gateway guide: Event Notification example has rendering breaks inside tokens; `CardType=m` lowercase vs uppercase in the table; several variables (`ExternalTransactionID`, `CurrencyCode`, `CardBIN`, chargeback reason fields, `ResponseCode`) have no description; `CreditCode="150"` is unexplained; DTD names vary (`three65api -authorize` with a space, `three65api-credit`, `Segpayapi-settle`); "Unique 10-digit" TransactionID vs 9-digit examples; Express Stats example uses `end_date` `2026-02-31` and contradicts its own date range text.
16. The 3DS V4 page says the authorization fields `ThreeDService`, `ThreeDSecure`, `SecureTransactionID` are "documented in the Gateway Integration Guide", but the published guide does not contain them.
17. Membership Upgrade JSON response example is not valid JSON (missing commas, curly quotes, `"newrecurringamount": "2021-07-15"`).
18. One-Click web service "Example Requests JSON" block is empty; its response format is NOT DOCUMENTED.
19. The SRS Data Availability chart lists a type "voice" (probably "void"); the declined SRS sample is missing `<` before `Data`; the transaction matrix says "Instant Conversation".
20. Which postback format the signed Gateway hosted pay page uses for its session-expired notice (Processing postback vs Gateway Event Notification) is not stated; field names `ResponseCode`, `ResponseCodeDescription`, `TransactionID` suggest the Gateway style.
21. Gated: real postback logs ("View Postbacks"), portal configuration, SRS/WSDL access with credentials, gateway admin test feature, valid state/country lists. Not attempted.
22. Online gaming wording is ambiguous (non-gambling on the home page vs "payouts to winners" on the gaming page); lead-form categories are not acceptance statements.
