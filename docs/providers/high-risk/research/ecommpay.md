# Ecommpay (adapter id `ecommpay`): high-risk candidate research

- Verification date: **2026-10-25**
- Gate outcome: **documentation_verified**
- Method: the developer portal publishes a Markdown mirror of every article (`https://developers.ecommpay.com/en/<id>.md`, listed in its own `llms.txt` index) and the Gate API as OpenAPI 3.0.2 JSON. Those pages and two files of the official PHP SDK were downloaded anonymously and read. No login, sign-up or access request was made. The marketing site `ecommpay.com` sits behind a bot-protection challenge that returns an empty script page to anonymous clients, so its pages could not be read and were not worked around.

## 5. Formats

- Content type: requests, responses and callbacks are UTF-8 JSON. Responses `application/json; charset=UTF-8`; callback example `Content-Type: application/json`, HTTP POST (en_gate_interaction_organisation).
- HTTP status: `200`, `400` (missing mandatory parameter), `403` (forbidden, e.g. IP), `422` (malformed JSON), `500` (platform error).
- Request status (response body `status`): `success` (accepted, async only) or `error`. This is not a payment status (en_faq_payment_result).
- Payment fields: `payment.id`, `payment.type`, `payment.status`, `payment.date`, `payment.method`, `payment.sum.amount` (minor units), `payment.sum.currency`, optional `region`, `is_new_attempts_available`, `cascading_with_redirect`, `merchant_refund_id`.
- Operation fields: `operation.id` (integer), `type`, `status`, `date`, `created_date`, `request_id`, `sum_initial`, `sum_converted`, `code` (string), `message`, `eci`, `provider` {`id`, `payment_id`, `date`, `auth_code`, `endpoint_id`, `result_code`, `result_message`}, optional `recurring_retry`.
- Status responses use an `operations` array; callbacks use a single `operation` object.
- Errors: request-level `{status:"error", code, message}`; platform rejections in an `errors` array of `{code, message, field, description}` (OpenAPI `ErrorItem` also has `constraint`); provider rejections in `operation.code`/`operation.message` (en_faq_payment_result).
- Amounts in minor units without separator; dates `YYYY-MM-DDThh:mm:ss+0000`.

Example A (sync error), transcribed from `DP`en_gate_interaction_organisation.md:

```json
{ "status": "error", "code": "2003", "message": "Invalid JSON string" }
```

Example B (async acceptance), same source:

```json
{
  "status": "success",
  "request_id": "e7cdefae67068d",
  "project_id": 69,
  "payment_id": "ORDER_ID__sendPurchase_dcc_1"
}
```

A full callback (two-step `auth` intermediate with `payment.status: "awaiting capture"`) is on `DP`en_platform_callbacks.md, "Common use cases".

## 6. Codes

Codes arrive in `operation.code` (string), `errors[].code`, or the top-level `code` of an error response. Category and retry columns are **suggestions** for PandaPayLens, not Ecommpay statements; they follow Ecommpay's "Action" column where it gives one. Ecommpay does not say the list is exhaustive; unknown codes must fall back to `unknown`.

### 6a. Status values

- Payment (`payment.status`), 23 values: `error`, `processing`, `awaiting 3ds result`, `awaiting merchant auth`, `awaiting redirect result`, `awaiting customer action`, `awaiting clarification`, `awaiting customer`, `awaiting capture`, `scheduled recurring processing`, `awaiting payout completion`, `awaiting payment`, `invoice sent`, `awaiting finalization`, `success`, `decline`, `canceled`, `partially reversed`, `reversed`, `partially refunded`, `refunded`, `expired`, `invoice canceled`.
- Operation (`operation.status`): `processing`, `awaiting 3ds result`, `awaiting merchant auth`, `awaiting redirect result`, `awaiting customer action`, `awaiting clarification`, `awaiting payout completion`, `awaiting payment`, `invoice sent`, `expired`, `invoice canceled`, `success`, `decline`.
- Request status: `success`, `error`. Token request: `success`, `error`; `token_status`: `active`, `expiry`, `revoke`. COF record `recurring.status`: `active`, `canceled`.
- Chargeback `chargeback_status`: example shows `WON`; full list NOT DOCUMENTED on pages read (refers to Data API).

## 7. Lifecycle

Model: a **payment** (merchant `payment.id`) contains one or more **operations** (`operation.id`). Payment status is the aggregate; operation status is per step (en_platform_payment_model_overview).

| Flow              | Operations                                                                | Payment statuses (beyond `processing`/awaiting)                                                                    |
| ----------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| One-step purchase | `sale`, optional `payment confirmation`, then `refund`/`reversal`         | `success`, `decline`, `error`, `partially reversed`, `reversed`, `partially refunded`, `refunded`                  |
| Two-step purchase | `auth` -> `capture` or `cancel`; `incremental` (only `success`/`decline`) | adds `awaiting capture`, `canceled`                                                                                |
| On-demand COF     | `recurring` (or `sale`)                                                   | `success`, `decline`, `error`, `reversed`, `partially refunded`, `refunded`                                        |
| Scheduled COF     | automatic debits, `recurring_update`, `recurring_cancel`                  | `scheduled recurring processing` while the series runs; refunds keep it unchanged until the series ends            |
| Payout            | `payout`, `payout reversal` (when crediting fails after `success`)        | `awaiting payout completion`, `success`, `decline`, `error`, `reversed`                                            |
| Verification      | `account verification`                                                    | `success`, `decline`, `error`                                                                                      |
| Payment link      | `invoice`, then `sale`/`auth`/`contract registration`                     | `awaiting payment`, `invoice sent`, `expired`, `invoice canceled`, `awaiting finalization`, plus purchase statuses |

- Refund vs reversal: within the operation day a full refund (any network) or any Mastercard refund becomes `reversal`; otherwise `refund` (en_platform_sms_model). Multiple refunds each get their own `operation.id`; `payment.sum.amount` shows the remaining amount (en_Gate_Refund).
- `awaiting 3ds result` and `awaiting clarification` time out to `decline` (usually 30 minutes).
- `awaiting customer` = retry attempts ("Try again") in progress.
- Chargebacks are not in payment callbacks; they arrive via the separate chargeback callbacks (events in section 8) or Data API. Stages: new, pre-arbitration, arbitration, cancelled by issuer, lost, won.
- Wallet semantics (Skrill, Neteller, AstroPay and others reached through `/v2/payment/wallet/...` and `/v2/payment/skrill/...`) use the same payment/operation model; APM declines use the `2xxxx` codes, card declines `1xxxx`.

## 8. Notifications

- Payment/operation callbacks: HTTP POST, JSON, UTF-8, `Content-Type: application/json` (example). Prescriptive callbacks (need action: `acs`, `threeds2.iframe`, `redirect_data`, `display_data`, `clarification_fields`) cannot be disabled; informational ones can (en_platform_callbacks).
- Event type field: **none**. Infer from `payment.status`, `operation.type`, `operation.status` and the presence of `acs`/`threeds2`/`redirect_data`/`clarification_fields`/`errors`.
- Required fields per table: `payment` (`id`, `status`, `type`), `project_id`, `signature`, `operation.request_id`, `operation.status`, `operation.type`, `account.number`, `customer.ip_address`. Projects can add, remove or rename optional fields; the structure and required fields stay.
- Signature (sensitive): `signature` at top level (token callbacks: `general.signature`). Algorithm: drop `signature`; flatten every value to `parent:...:name:value`; booleans to `1`/`0`; array items indexed from 0; empty arrays skipped; empty values kept; natural sort; join with `;`; HMAC-SHA512 with the project secret key; Base64 (en_platform_signature). The PHP SDK also escapes `:` in keys as `::`, removes nested `signature` keys and ignores `frame_mode` (SignatureHandler.php, Callback.php). PandaPayLens should never verify (no key) and should mask the value.
- Acknowledgement: HTTP `200 OK` (body optional; example shows `OK`, `text/plain`). Any other answer triggers a resend.
- Retry: 6 attempts at 10-60 s, 58 attempts growing to 2.5 h, then every 4 h up to 120 attempts, within about 11 days. Resent callbacks may carry **newer** data if the status changed. Optional delay 0-600 s (`callback.delay`); can be disabled per request (`callback.force_disable`).
- Ordering: NOT DOCUMENTED. Duplicate identification: no delivery ID; use `operation.id` + `operation.status` + `operation.date` (heuristic).
- Token callbacks: `general` {`project_id`, `customer_id`, `signature`}, `request` {`id`, `action`, `status`, `errors`}, `token`, `token_created_at`, `token_status`.
- Chargeback callbacks: **unsigned**, daily at 12:00 UTC (fallback 15:00), one URL per project, never resent. Summary events `new_chargebacks_summary`, `new_pre_arbitration_summary`, `new_arbitration_summary` (`event`, `event_date`, `project_id`, `merchant_id`, `chargeback_count`). Detailed events `new_chargeback_details`, `new_pre_arbitration_details`, `new_arbitration_details`, `chargeback_cancelled_by_issuer`, `chargeback_lost`, `chargeback_won` with `chargebacks[]` (`chargeback_id`, `case_id`, `operation_id`, `arn`, `card_type`, `chargeback_status`, `reason_code`, dates, amounts).

## 11. Structural detection hints

Strong Ecommpay signals (combine several):

1. JSON with top-level integer `project_id`, a `payment` object (`id`, `type`, `status`) and either `operation` or `operations[]`, plus top-level `signature` (Base64, 88 characters for HMAC-SHA512).
2. Status strings with spaces: `awaiting 3ds result`, `awaiting capture`, `partially refunded`, `scheduled recurring processing`, `invoice sent`.
3. Operation objects with `sum_initial` + `sum_converted`, `request_id`, `provider` {`id`, `payment_id`, `endpoint_id`, `auth_code`}, and `code` as a numeric string (`"0"`, `"3061"`, `"10105"`).
4. Error body exactly `{status:"error", code, message}`; acceptance body `{status:"success", request_id, project_id, payment_id}`.
5. Token callback: `general` + `request.action` in `tokenize|token_revoke` + `token_status`.
6. Chargeback callback: `event` in the nine values above with `event_date`, `merchant_id`.
7. Hosts and paths: `api.ecommpay.com`, Gate paths `/v2/payment/...`.

Versus supported providers: Stripe uses `object`, prefixed IDs and dotted `type`; Adyen uses `pspReference`, `resultCode`, `notificationItems`; payabl. is URL-encoded (`transactionid`, `errorcode`, `security`); PayPal has `event_type` + `resource`; Braintree posts `bt_signature`/`bt_payload`; Mollie and Square use prefixed IDs or `data.object`. **Code collision**: Checkout.com `response_code` `10000` means approved, while Ecommpay `10000` is a generic decline; never decode a bare 5-digit code without structure. Versus other candidates (emerchantpay, Paymentwall, NMI, MiFinity, AstroPay, Skrill): none were researched here; note that Ecommpay itself offers Skrill, Neteller and AstroPay as payment methods, so such payments reach the merchant in Ecommpay's own JSON (with `payment.method`), not in those providers' native formats.

## 12. Limitations, ambiguities, inconsistencies

1. Callback content is configurable per project (fields added, removed, renamed); only the required set is reliable.
2. No event type or delivery ID; resends may contain newer data; ordering NOT DOCUMENTED.
3. Two code locations with different types: `operation.code` is a string, `errors[].code` is an integer in OpenAPI `ErrorItem` but quoted strings in examples.
4. Code `3201` means "payment routing error" in the table, but the status-request page shows it with a field validation message (`booking_info.start_date cannot be empty`).
5. Refund page says the refund ID is in an `operation_id` parameter inside `operation`; its examples show `operation.id`.
6. Payment type spelling: `account_verification` in `payment.type`, `account verification` in `operation.type`; Dashboard filter also lists `account verification`.
7. Status responses use `operations[]`; some status examples use a single `operation` object plus `last_failed_request`.
8. OpenAPI `ProviderResultInfo.payment_id` reuses the merchant `payment_id` description although it is the provider's ID.
9. Docs examples include invalid JSON (e.g. `"endpoint_id": 0000` in the signature page, missing commas in callback examples) and truncated signatures with `...`.
10. Request example sends a JSON body with `Content-Type: application/x-www-form-urlencoded`.
11. Spec `info.version` 3.38.1 while the index changelog mentions 3.38.2.
12. Chargeback callbacks are unsigned and never resent; full `chargeback_status` values are only in the Data API (not read).
13. Marketing site pages (industries, licences, about) were unreadable due to bot protection; sector and licence data are therefore incomplete.
