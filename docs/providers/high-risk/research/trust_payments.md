# Trust Payments (adapter id `trust_payments`): high-risk provider research

Status: research notes for a parse-only PandaPayLens adapter. Nothing here is a guarantee about live behavior. Everything comes from Trust Payments' first-party documentation, its official website and its official client library as published on the verification date. When a point is not documented, the text says **NOT DOCUMENTED**. Suggested categories and retry classes are suggestions, not Trust Payments statements.

- Verification date: **2026-10-25**
- Gate outcome: **`documentation_verified`** (see section B)
- Method: the Trust Payments Help Centre (help.trustpayments.com, a Zendesk help centre) was read through its own public, unauthenticated Help Center API (`/api/v2/help_center/en-us/...`), which returns the same article bodies as the HTML pages. Every article in the "TRU Connect" developer category (339 articles), the "Security and Compliance" category and the "Acquiring" category was downloaded; the articles listed in section A were read in full. All 505 downloaded articles carry `user_segment_id: null`, i.e. they are public. The legacy reference pages on `webapp.securetrading.net` (linked from the Help Centre) and the official Python client library on GitHub were also read. No login, signup or access request was made. No provider endpoint was called.
- Brand note: Trust Payments is the current name of the business formerly trading as **Secure Trading** (the Malta entity "has been operating from Malta since 2014 under the name of Secure Trading Financial Services Ltd", trustpayments.com/malta). The technical platform still uses the legacy names everywhere: endpoints on `securetrading.net`, the reference pages titled "STPP" (Secure Trading Payment Platform), test issuer names `SecureTrading Test Issuer1`, the PyPI package `securetrading`, the Composer package `securetrading/stpp_json` and the GitHub organisation `SecureTrading`. The gateway product is branded **TRU Connect**; the merchant portal is **Portal** (formerly **MyST**). Real pasted payloads may contain any of these names.

## 3. Response and error formats

### 3.1 Content types and encoding

- **JSON responses**: UTF-8 ("All responses from us are encoded using UTF-8", Build your own solution). All values are **strings**, including numbers (`"errorcode":"0"`, `"baseamount":"1050"`, `"settlestatus":"100"`). The `response` member is always an **array**; a multi-request call (e.g. `["THREEDQUERY","AUTH"]`) returns one element per request type processed.
- **XML responses**: `<responseblock version="3.67">` with `<requestreference>`, one or more `<response type="AUTH">` elements and `<secrand>`. Field locations follow the XPaths in each field table (e.g. `errorcode` is `/error/code`, `settlestatus` is `/settlement/settlestatus`, `requesttypedescription` is `/@type`).
- **URL notifications**: "Content-type: application/x-www-form-urlencoded; charset=UTF-8", field names and data URL-encoded.
- **HTTP status codes** of the Webservices API: **NOT DOCUMENTED**. Errors are returned inside the response body via `errorcode`.
- **Error shape**: there is no separate error envelope. An error is the same response object with a non-zero `errorcode`, an `errormessage`, optionally `errordata`, and sometimes `requesttypedescription: "ERROR"` (when the request could not be processed as the requested type).

## 4. Codes

Field location: `errorcode` (JSON, notifications, redirects) or `/error/code` (XML), with `errormessage` (`/error/message`) and `errordata` (`/error/data`). Category and retry columns are **suggestions**. Where Trust Payments gives advice, it is reflected and noted ("TP:").

## 5. Lifecycle

### 5.1 Settle status (gateway-level, card payments)

| `settlestatus` | Portal label                | Meaning                                                                                                                                                       | Can update?                                         |
| -------------- | --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `0`            | Pending                     | Authorised, will settle automatically; may still be suspended by fraud/duplicate checks                                                                       | yes (to 1, 2, 3; amount, due date, order reference) |
| `1`            | Manual                      | Authorised, will settle; bypasses internal fraud and duplicate checks                                                                                         | yes                                                 |
| `2`            | Suspended                   | Will not settle without merchant action; auto-cancelled (to 3) 7 days after authorisation (31 for pre-auths). A REFUND not settled within 5 days is cancelled | yes (to 0, 1, 3)                                    |
| `10`           | Settling                    | Sent to the acquirer; typical for APMs (may take days). Merchant cannot set it (error `60025`)                                                                | no                                                  |
| `100`          | Settled                     | Batched and sent to the acquirer. Does not guarantee funds have reached the merchant. Merchant cannot set it (error `30000`). Refundable                      | no                                                  |
| `3`            | Decline / Cancelled / Error | Will not settle; check `errorcode`                                                                                                                            | no                                                  |

Card payment path: AUTH `0` (or `1`) then `10` then `100`; or `2` (suspended) then back to `0`/`1` or to `3`; or `3` directly on decline/error. Authorisations reserve funds for 7 days (31 for `authmethod=PRE`). `authmethod` does not change settle status.

APM path (iDEAL example): AUTH returns `settlestatus=10` with a `redirecturl`; a URL notification later reports `3` or `100`.

SCHEMEUPDATE path: `0` on acceptance, `10` once sent to the schemes, then `100` (checks done) or `3` (issue; with `errorcode=70000` it means the cardholder stopped recurring payments).

### 5.2 Payment (authorisation) outcomes

`errorcode=0` with `settlestatus` 0/1 = authorised; `70000` = declined (settle status 3); `71000` = soft decline needing 3DS; `60010`/`60034`/`99999` = outcome unknown. There is no separate capture request: settlement is a daily batch of pending AUTHs. Amount reduction before settlement is done with TRANSACTIONUPDATE `settlebaseamount`. Cancellation ("void") before settlement = TRANSACTIONUPDATE `settlestatus=3`.

### 5.3 Refund

REFUND is a child of a settled AUTH (`settlestatus` 100) via `parenttransactionreference`; partial refunds allowed up to the settled amount. Online refunds (Visa; Mastercard from 2025-11-04) get an issuer decision (`70000` if declined); offline refunds return `authcode` `REFUND ACCEPTED` and settle later. A REFUND gets its own `transactionreference` and its own settle status.

### 5.4 Recurring and subscription

- **Merchant-driven recurring**: parent AUTH or ACCOUNTCHECK (`credentialsonfile=1`, `subscriptiontype`, `subscriptionnumber=1`), then child AUTHs with `accounttypedescription=RECUR`, `parenttransactionreference` = the parent AUTH/ACCOUNTCHECK (never the THREEDQUERY), `credentialsonfile=2`, `subscriptionnumber` incremented. `acquireradvicecode` may come back on child responses.
- **Subscription Engine**: combined `["THREEDQUERY","AUTH","SUBSCRIPTION"]` or `["THREEDQUERY","ACCOUNTCHECK","SUBSCRIPTION"]`. The SUBSCRIPTION is a record with its own `transactionreference`; the engine runs daily and creates AUTHs with `accounttypedescription=RECUR`. Subscription state (`active` / `transactionactive`): `0` inactive (re-enabling catches up missed payments), `1` active, `2` pending until the first payment settles, `3` stopped (permanent; set automatically when VAU/ABU reports a cardholder cancellation). If the initial AUTH declines, no SUBSCRIPTION response is returned. A subscription is complete when `subscriptionnumber` > `subscriptionfinalnumber`; `subscriptionfinalnumber=0` means indefinite.
- **Cancellation**: TRANSACTIONUPDATE of the SUBSCRIPTION to `active` 0 or 3; or scheme-driven stop (SCHEMEUPDATE `3` + `70000`).

### 5.5 Payouts

Payouts are `requesttypedescription=REFUND` with `accounttypedescription=CFT`, optionally referencing a previous transaction by `parenttransactionreference`. They get their own `transactionreference` and settle status (example: `100`). Mastercard duplicate-payout outcomes surface via `acquireradvicecode` 6/7/80.

### 5.6 Request types seen in the documentation

`AUTH`, `REFUND`, `ACCOUNTCHECK`, `THREEDQUERY`, `THREEDLOOKUP`, `THREEDRESULT`, `SUBSCRIPTION`, `TRANSACTIONQUERY`, `TRANSACTIONUPDATE`, `SCHEMEUPDATE`, `RISKDEC`, `CURRENCYRATE`, `ORDER`, `ORDERDETAILS`, plus `ERROR` (response only). `CHARGEBACK` is implied by error `20021` but is **NOT DOCUMENTED** as a request or record type.

### 5.7 Chargebacks

Chargebacks are handled at the acquiring level and viewed or exported in Portal ("Chargebacks" page, CSV/XLSX) and the RAM Tool. No chargeback URL notification or API payload is documented. Stages documented: first chargeback (dispute), re-presentment, pre-arbitration, arbitration, pre-compliance, Rapid Dispute Resolution. Reason codes are described by category only (no numeric table). For PandaPayLens this is out of scope.

### 5.8 Wallets

Apple Pay and Google Pay are payment types on the card flow (`walletsource` e.g. `APPLEPAY`, `walletdisplayname`); no separate wallet lifecycle.

## 6. Notifications / postbacks / webhooks

### 6.1 Delivery

- Configured either per request on Payment Pages with system rules (`ruleidentifier` `STR-8` successful, `STR-9` declined, `STR-10` all, with `successfulurlnotification` / `declinedurlnotification` / `allurlnotification`) or in Portal's Rule Manager ("URL notification" action with conditions on account type, request type, payment type, currency, settle status, error code).
- HTTPS POST, port 443, valid CA-signed certificate required for live. Source IP range 3.250.209.64/26.
- Merchant must reply **HTTP 200** within **8 seconds**.
- Three flows: **online** (sent during the transaction, customer waits, no retry), **offline** (queued after the response, retried for about 48 hours), **failover** (sent during the transaction, queued for retry on failure). Only the first online notification is sent synchronously if several qualify.
- "One notification is sent per request". After 48 hours without confirmation, an email is sent ("Notification Problems", from support.stpp@securetrading.com).
- Sources of notifications: payments (any integration), Subscription Engine AUTHs (one per transaction), SCHEMEUPDATE results (one per update, enabled by Support), APM settlement updates.
- Ordering guarantees: **NOT DOCUMENTED**. A timestamp of the notification itself: **NOT DOCUMENTED** (include `transactionstartedtimestamp` as a field if configured).

### 6.2 Fields

- Body: `application/x-www-form-urlencoded; charset=UTF-8`, flat `name=value` pairs; a field can repeat (`fieldname=bravo&fieldname=alpha`).
- Always present: `notificationreference` (e.g. `1-A60356`).
- STR rule defaults: `transactionreference`, `requestreference`, `orderreference`, `sitereference`, `errorcode`, `settlestatus`, `paymenttypedescription`, plus `responsesitesecurity`. Extra fields via `stextraurlnotifyfields`.
- Rule Manager actions: field set chosen by the merchant. Trust Payments recommends at least `acquirerresponsecode`, `acquirerresponsemessage`, `authcode`, `baseamount`, `currencyiso3a`, `errorcode`, `livestatus`, `orderreference`, `parenttransactionreference`, `paymenttypedescription`, `requesttypedescription`, `settlestatus`, `sitereference`, `transactionreference`. Custom field names are allowed.
- There is **no event-type field**. The "event" must be inferred from `requesttypedescription` + `errorcode` + `settlestatus` (and `accounttypedescription`, e.g. `RECUR` for engine payments).
- Payment Pages browser redirects (STR-6/7/11/12/13 or "Payment pages redirect" actions) carry the same default fields and `responsesitesecurity`; minimum recommended `errorcode`, `settlestatus`, `transactionreference`. Whether redirects are GET query strings or POSTs: **NOT DOCUMENTED** in the pages read.

### 6.3 Signature (sensitive; PandaPayLens must not verify)

`responsesitesecurity` = lowercase hex SHA-256 of: the **values** (URL-decoded, whitespace kept) of all fields except `notificationreference` and `responsesitesecurity`, concatenated in ASCII order of **field name**, followed by the notification password. Blank fields are omitted; repeated fields are concatenated in the order sent. Unlike the request `sitesecurity` (prefixed `h`), the response hash has no prefix. Both documented worked examples are internally consistent (checked offline). Response JWTs are signed HS256 with the merchant's JWT secret ("We do not support the signing of tokens with a private key").

### 6.4 Duplicate identification

"If we fail to receive a response to an offline or failover notification, the notification will be resent with the same notification reference". So **`notificationreference`** is the dedupe key for redelivery. The business object key is `transactionreference`. Duplicate _payment_ detection by the gateway (duplicate checks) suspends identical payments within 15 minutes (settle status 2).

## 8. Sensitive fields

Redact or mask by default (requests are included because developers paste request/response pairs):

- **Card data**: `pan` (full PAN in Webservices requests), `securitycode`, `expirydate`, `maskedpan` (masked; keep BIN/last4 policy), `customeraccountnumber` (can be a full card or bank account number in requests), `issuenumber`.
- **3DS / cryptograms**: `cavv`, `tavv`, `eci` (low risk), `threedpayload`, `acsurl`, `cachetoken`, `threedstransactionid`.
- **Secrets / auth material**: `responsesitesecurity`, `sitesecurity` (request hash), the notification/site security password, the HTTP `Authorization: Basic ...` header (base64 of Web Services username:password), `alias` and `operatorname` (Web Services username, e.g. an email), the request and response JWT (and the JWT secret), `acquirersecret` (APM responses), `redirecturl`.
- **Personal data**: `billingfirstname`, `billinglastname`, `billingmiddlename`, `billingprefixname`, `billingsuffixname`, `billingemail`, `billingtelephone`, `billingpremise`, `billingstreet`, `billingtown`, `billingcounty`, `billingpostcode`, `billingcountryiso2a`, all `customer*` delivery fields, `customerdob`, `customerip`, `customerlastname`, `customerpostcode`.
- **Merchant identifiers**: `sitereference`, `merchantnumber`, `tid`, `merchantname`, `facilitatorid`, sub-merchant fields, notification/redirect URLs.

## 9. Structural detection hints

Strong Trust Payments signals (combine several):

1. **JSON envelope**: top-level keys `requestreference`, `version` (`"1.00"`), `response` (array), `secrand`. Library output uses `responses` instead of `response`. Decoded JWT payload: `{"iat", "payload": {"requestreference","version","jwt","response":[...],"secrand"}, "aud"}`.
2. **Field vocabulary** inside response objects: `requesttypedescription` (values `AUTH`, `THREEDQUERY`, `ACCOUNTCHECK`, `TRANSACTIONQUERY`, `ERROR`, ...), `accounttypedescription` (`ECOM`/`MOTO`/`RECUR`/`CFT`), `settlestatus`, `settleduedate`, `transactionreference`, `parenttransactionreference`, `baseamount`, `currencyiso3a`, `livestatus`, `securityresponse*`, `paymenttypedescription`, `maskedpan` with `#` masking, `issuercountryiso2a`, `transactionstartedtimestamp`. The `...iso2a` / `...iso3a` suffixes and `...description` naming are highly distinctive.
3. **Reference shape**: `transactionreference` matching `^\d+-\d+-\d+$`; `notificationreference` like `1-A60356`; `requestreference` like `W23-fjgvn3d8`.
4. **Code shape**: 5-digit `errorcode` strings (`30000`, `70000`, `71000`, `60010`, `22000`) with `errormessage` `Ok` on success.
5. **XML**: root `<responseblock version="3.67">` with `<response type="AUTH">`, `<error><code>`, `<settlement><settlestatus>`, `<secrand>`; requests `<requestblock version="3.67">` with `<alias>`.
6. **Notifications**: form-encoded with `notificationreference=`, `responsesitesecurity=` (64 hex), `transactionreference=`, `settlestatus=`, `sitereference=`.
7. **Hosts/strings**: `webservices.securetrading.net`, `payments.securetrading.net`, `webapp.securetrading.net`, `cdn.eu.trustpayments.com`, `SecureTrading Test Issuer1`, `test_site12345`, `jwt.user`, `webservices@example.com`.

How this differs from supported and candidate providers:

- **payabl.**: also form-encoded with `errorcode`/`errormessage`, but uses `transactionid`/`transid`, `orderid`, `type=order|capture|refund`, `security`, negative codes (`-6000`, `-5004.03a`) and `status=2000` for pending. Trust Payments never uses `transactionid`; its codes are positive 5-digit numbers; it uses `transactionreference`, `settlestatus`, `notificationreference`, `responsesitesecurity`.
- **Stripe / Adyen / Checkout.com / PayPal / Braintree / Mollie / Square**: camelCase or object-typed JSON (`object`, `pspReference`, `resultCode`, `event_type`, `type` with dotted names). Trust Payments is all-lowercase concatenated names with string values and an array `response`.
- **Verotel** (candidate): form-encoded postbacks with `transactionID`, `saleID`, `signature`; no `errorcode`.
- Other candidates (Decta, Ecommpay, emerchantpay, PXP, etc.): not compared field by field here; confidence should rise only when several of the signals above co-occur.
- False-positive risk: third-party platforms that integrate Trust Payments may re-emit these names inside their own envelopes. That is outside Trust Payments' documentation.

## 10. Limitations, ambiguities and documentation inconsistencies

1. **Error list is terse**: 255 codes with one-line messages and no retry guidance except for the handful in 4.1. Several messages are placeholders (`{0}`), generic ("Missing", "Payment Error"), or identical across 21 codes (`60100`-`60120` "Invalid process").
2. **Client vs server codes share one space**: codes 1-10 come from Trust Payments' client libraries, not from the gateway; codes 31000-31010 and 51000/51001 are customer-facing messages (Payment Pages style).
3. **`50000` message conflict**: the error list says "Socket receive error", while the JSON Web Token article gives "errorcode 50000, errormessage Timeout" as an example (the list has `50005` = Timeout).
4. **Acquirer advice code width**: AUTH and TRANSACTIONQUERY tables say `Numeric (1)` with values 0, 1, 2, 4, 8; the dedicated mapping article lists 23 values up to `99`.
5. **Subscription status field naming**: the FAQ calls it `active` with values 0-3; the TRANSACTIONQUERY-for-subscriptions table calls it `transactionactive` and documents only 0-2.
6. **`response` vs `responses`**: raw JSON uses `response`; the Python/PHP library examples (and real library output) use `responses`. An adapter should accept both.
7. **Acquirer response codes** (`acquirerresponsecode`, `acquirerresponsemessage`, `schemeresponsecode`) vary by acquiring bank and have no published table. Decline reasons beyond `70000` therefore depend on undocumented acquirer codes.
8. **No HTTP status semantics** for the Webservices API and no notification event-type field; event meaning must be inferred.
9. **Notification ordering**, notification timestamps, and the redirect transport method are **NOT DOCUMENTED**. Field sets in notifications are merchant-configurable, so only `notificationreference` is guaranteed; the STR defaults are the best baseline.
10. **Chargebacks** are not exposed through the gateway API or notifications; `20021` hints at internal chargeback records but the type is undocumented.
11. **Protect Plus `fraudcontrolresponsecode`** values (e.g. `0100`, `0150`) have no published mapping.
12. **Example data quality**: some XML examples mix values from different examples (e.g. `issuercountry` `ZZ` in XML vs `US` in JSON for the "same" response); the THREEDLOOKUP XML example has a mismatched closing tag (`<transactionid>...</version>`) and a doubled `</responseblock>`. The 3DS field table spells "Alphanumeirc" and "THEEDQUERY". Treat examples as illustrative.
13. **Timestamps** have no documented time zone (the Payment Pages `sitesecuritytimestamp` must be UTC, but response timestamps are not stated).
14. **Feature availability is acquirer-dependent** (many fields "returned if provided by the acquiring bank"), so absence of a field is not meaningful.
15. **Brand mixture**: Trust Payments, TRU Connect, Secure Trading, STPP, MyST and Portal all refer to the same platform; legacy names will appear in real payloads and emails.
